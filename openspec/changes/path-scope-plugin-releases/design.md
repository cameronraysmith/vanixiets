## Context

See brainstorm.md for the full source-grounded investigation trail (Q1-Q8). Summary of what constrains this design:

- The 18 first-party plugin packages' monorepo-subpath dependencies (`apm.yml:80-98`) pin `#main`; `apm.lock.yaml` records `resolved_ref: main` for all 18 (`apm.lock.yaml:8-9` and 17 similar blocks), so `apm outdated` fires on every commit to `main` regardless of what it touches.
- Docs already release path-scoped (`packages/docs/package.json:66-129`, `extends: semantic-release-monorepo`), tagged `@vanixiets/docs-v*.*.*` by that plugin's default `<package-name>-v<version>` tag format.
- Release execution moved entirely to hercules-ci effects under nixbot/buildbot-nix (`modules/effects/vanixiets/herculesCI/release-packages.nix`, `deploy-docs.nix`); the GH-Actions release pipeline is retired (`.github/deprecated/{cd,ci-nix-fast-build,ci-pre-nix-check,package-release,deploy-docs}.yaml`). GH Actions remains live for scheduled/triggered maintenance-bot workflows (`update-flake-inputs.yaml`, `regenerate-lock-files.yaml`).
- `apm`'s own revision-pin logic (verified against source, `~/ghq/github.com/microsoft/apm` tag `v0.29.0`, matching the installed `apm --version` = 0.29.0) fail-closes a full-SHA pin's staleness check unless the underlying tag is *annotated* (`apm_cli/deps/revision_pins.py:120-121`), and this repo's release tooling — both core `semantic-release` (`lib/git.js:227-229`) and the already-adopted `semantic-release-major-tag` (`dist/steps/success.js:29-33`) — creates only *lightweight* tags.
- The actual deployed skill tree (`apm-skills-compose/package.nix`) never resolves these 18 deps via GitHub at all; it copies the local worktree in as path deps (`package.nix:83-99`). Only `apm-skills-install.sh` (a `nix run` app, not a sandboxed derivation) consumes the root `apm.yml`/`apm.lock.yaml` GitHub-subpath pins.

## Goals / Non-Goals

**Goals:**
- Give `apm outdated` a real, per-dependency staleness signal for the 18 first-party plugin packages, grounded in whether `modules/home/ai/plugins/` actually changed.
- Make relocking a deliberate act triggered by an actual plugins release, not an incidental side effect of any commit to `main`.
- Reuse existing tooling and infrastructure (`semantic-release-monorepo`, `semantic-release-major-tag`, the `release-packages` hercules-ci effect, GH-Actions maintenance-workflow pattern) rather than introducing new release machinery.
- Notify a human with an actionable artifact (a pull request) when the plugins tree's release tag advances.

**Non-Goals:**
- Actually cutting the first `@vanixiets/plugins-v1.0.0` release or running the first post-release relock — that is follow-on implementation work sequenced in the Migration Plan below, outside this change's planning-only scope.
- Building new apm-side tooling (an annotated-tag creation step, a consumer-side `tag_pattern` override) to make the full-SHA revision-pin path work. D2 below explains why the literal-tag-ref path is sufficient without it; adding annotated tagging is recorded as a rejected-for-now alternative, not built.
- Changing docs' existing release line, the hercules-ci effect definitions themselves, or anything under `.github/deprecated/`.
- Independent per-directory versioning of the 18 plugin packages. This design is deliberately lockstep (one release, one version, 18 alias tags at the same commit) — see D3's trade-off note.

## Decisions

### D1: Release-line package location — `modules/home/ai/plugins/package.json`, not `packages/plugins/package.json`

- **Choice**: Create the new release-scoped `package.json` directly inside `modules/home/ai/plugins/`, alongside the 18 plugin package directories it releases.
- **Rationale**: `semantic-release-monorepo` scopes commit analysis to "a file in or below a package's root" (vendored README, lines 13-17), where "root" is literally the directory `semantic-release` is invoked from — `release.sh`'s `cd "$package_path"` (`release.sh:175`). The directory we actually want to gate releases on is `modules/home/ai/plugins/`. Placing the package.json anywhere else (in particular under `packages/`, following the docs precedent's directory convention) would scope commit analysis to that other directory instead, never firing on real plugin changes.
- **Alternatives considered**: `packages/plugins/package.json`, matching the existing `packages/<name>` convention `list-packages-json.sh` already expects with zero script changes. Rejected: this would scope releases to commits under `packages/plugins/**`, a directory with no first-party skill content — the release line would never fire on the changes it exists to track. Convention-matching is not worth shipping a mechanism that structurally cannot do its job.

### D2: Dependency ref form — literal per-package alias tag, not a full 40-char SHA

- **Choice**: Repoint each of the 18 first-party deps' `ref:` in `apm.yml` from `main` to its own literal alias tag (e.g. `ref: planning-and-development-v1.0.0`), not the commit SHA that tag resolves to.
- **Rationale**: `apm outdated`'s two staleness-check paths behave differently. The full-SHA path (`is_full_revision_pin` → `find_latest_annotated_tag`) requires an *annotated* tag (`revision_pins.py:120-121`, described in-source as a "fail-closed security fence"); this repo's tags are all lightweight (D-verified in Context above), so a SHA pin would make every one of these 18 deps report `status: unknown` forever — never `outdated`, defeating the entire purpose. The literal-tag-ref path (`_check_one_dep`'s `is_tag_ref` branch, `outdated.py:319-370`) does not filter on annotation at all, so it is the only path that produces a genuine signal without new apm-side tooling.
  This is a deliberate, scoped departure from the repo-wide manifest convention "the full 40-char SHA is required; a short ref forces a network fetch" (repeated in `version-control-and-forge/apm.yml`, `planning-and-development/apm.yml`, etc.). That convention exists to keep the network-isolated `apm-skills-compose` nix derivation buildable offline. The 18 first-party deps are never resolved inside that derivation (Context, last bullet) — they are resolved only by `apm-skills-install.sh`, a `nix run` app that already has network access for its non-`--frozen` path. `apm install --frozen` (the steady-state, offline path) reads `resolved_commit` from the lockfile regardless of the manifest ref's form (`install.py:1767-1774`, `bare_cache.py:440-445`), so this departure changes relock-time behavior only, never materialization.
- **Alternatives considered**:
  - Full-SHA pin (matches blanket convention). Rejected: produces `unknown` forever under this repo's lightweight-tag tooling (verified against apm source, not assumed) — does not achieve the stated goal.
  - Full-SHA pin plus new tooling to make release tags annotated (a custom `git tag -a` step alongside `semantic-release-major-tag`'s `git tag --force`). Rejected for this change: real engineering (a new release-side script or plugin), and D2's chosen literal-tag-ref path achieves the goal without it. Recorded in Open Questions as a future option if the literal-tag-ref departure proves unacceptable to the maintainer.
  - Single shared literal tag (e.g. all 18 deps pinned to `@vanixiets/plugins-v1.0.0`). Rejected: apm derives the tag-pattern `{name}` from the dependency's own final path segment for virtual subdirectory deps (`revision_pins.py:87-91`, confirmed independently in apm's own docs, `reference/cli/outdated.md:23`), not from any shared prefix, and there is no consumer-side override for a `dependencies.apm` list-form entry (the only `tag_pattern` override apm documents is on the marketplace *producer* side, which these deps deliberately bypass). A shared tag would never match any dependency's inferred `{name}-v{version}` pattern.

### D3: Tag naming — canonical `@vanixiets/plugins-v*.*.*` plus 18 per-package alias tags via `semantic-release-major-tag`

- **Choice**: The release package is named `@vanixiets/plugins` (package.json `name`), giving the canonical semantic-release tag `@vanixiets/plugins-v<version>` via `semantic-release-monorepo`'s default tag format. The same release additionally mints 18 lightweight alias tags, one per plugin directory, named exactly `<group>-v<version>` (bare, no `@vanixiets/` prefix — e.g. `planning-and-development-v1.0.0`), via `semantic-release-major-tag`'s `customTags` option (already a devDependency, already used at root for `v${major}`/`v${major}.${minor}`; its README documents arbitrary literal-text-plus-placeholder templates, `README.md:33-49`).
- **Rationale**: The canonical tag names the release consistently with `@vanixiets/docs-v*.*.*` (npm-scope-style, matching this repo's existing convention and the `plugins/` directory name it releases). The 18 alias tags must be bare group names with no prefix because that is exactly what apm's `{name}` inference produces for each dependency (D2); any prefix or suffix would break the match.
- **Alternatives considered**:
  - `@vanixiets/skills-v*.*.*` as the canonical name (matching "skills," the deployed-artifact vocabulary, rather than "plugins," the source-directory vocabulary). Rejected in favor of `plugins`: the actual directory is `modules/home/ai/plugins/`, and existing infra already uses "plugin" for this concept (`pkgs/by-name/agent-plugins/`, `structure-mergify-release-alignment`'s "agent-plugins" naming). Using "plugins" keeps the release-line name aligned with the directory and existing package-naming vocabulary rather than introducing a second term for the same referent.
  - Bare `v*.*.*` alias tags (no name prefix at all — matches apm's `v{version}` default pattern, which is name-agnostic and would trivially match for every dependency). Rejected: the root `package.json` already reserves `v${major}`/`v${major}.${minor}` floating tags (`package.json:82-88`) for its own (possibly-dead — see Open Questions) release identity; a bare `v*.*.*` per-plugins-release tag would collide with that namespace and also carries no information about which package it names, unlike the per-group alias.

### D4: Notification mechanism — tag-triggered GitHub Actions workflow opening a PR, not a scheduled `apm outdated` run

- **Choice**: A new GH Actions workflow triggered on `push: tags: ['@vanixiets/plugins-v*']` runs `just agents-relock` and opens a pull request carrying the diff, following `regenerate-lock-files.yaml`'s existing amend-and-push pattern (`.github/workflows/regenerate-lock-files.yaml:42-70`).
- **Rationale**: This repo has no existing scheduled `apm outdated` check anywhere (live or deprecated) to extend, and D2/D3's alias-tag mechanism, while it does make `apm outdated` accurate when run by hand, is not itself a notification — nobody runs it proactively. A tag push is the exact, unambiguous "the plugins tree released" event; wiring it directly to a relock-and-PR workflow gives a human a reviewable artifact rather than a status line they have to think to check. GH Actions remains live infrastructure for this class of maintenance-bot workflow in this repo (`update-flake-inputs.yaml`, `regenerate-lock-files.yaml`), distinct from the retired GH-Actions *release* pipeline.
- **Alternatives considered**: Extending `update-flake-inputs.yaml`'s cron schedule to also run `apm outdated`/`agents-relock` unconditionally. Rejected: decouples the notification from the actual release event, reintroducing a form of the original noise problem (relock attempted on a schedule regardless of whether anything changed) rather than tying it to the event that matters.

## Risks / Trade-offs

- [Risk] Lockstep versioning: because all 18 alias tags advance together at whatever commit `semantic-release-monorepo` decides deserves a release (based on commits under `modules/home/ai/plugins/**` as a whole, not per-subdirectory), a change to one plugin directory bumps and retags all 18. → Mitigation: this is still a dramatic improvement over the current "all 18 flagged on any commit to `main`" — the discharge boundary narrows from "the whole repo" to "the plugins tree," not to a single subdirectory. Per-directory independent versioning was considered and rejected (see Non-Goals) as disproportionate ceremony for directories with no independently publishable npm content.
- [Trade-off] Departing from the blanket full-SHA manifest convention for these 18 deps only, accepted because the offline-build rationale behind that convention is verified not to apply to this dependency class (D2) — but this creates a second, precedent-setting pinning style in the same manifest family that a future contributor could misapply to a *genuine* third-party dependency that does live inside the sandboxed compose derivation. → Mitigation: tasks.md includes writing an explicit manifest comment on each repointed entry (matching the existing per-entry comment convention already used elsewhere in these files) stating the exception and its justification, so the departure is locally documented rather than only living in this design doc.
- [Risk] `list-packages-json.sh`'s generalization, if implemented as a broad recursive glob rather than an explicit second discovery root, could pick up an unintended `package.json` (for example a stray `node_modules` under a plugin's `.apm/skills/` reference tree, or a future unrelated file). → Mitigation: tasks.md specifies an explicit, additive second discovery root (`modules/home/ai/plugins/package.json` checked directly, not a recursive find), matching the existing script's flat, non-recursive `packages/*/package.json` pattern rather than introducing a new discovery strategy.
- [Trade-off] 18 additional lightweight tags per release grows the tag namespace continuously. → Accepted: lightweight tags are cheap, and the namespace is bounded by the (slowly growing) count of first-party plugin directories, which is itself tracked in version control.

## Migration Plan

This change delivers planning artifacts only; the following is the sequencing a follow-on implementation change would execute, recorded here so the design is actionable and its steps are independently verifiable, per tasks.md:

1. Generalize `list-packages-json.sh` to also discover `modules/home/ai/plugins/package.json`, verified by running it and observing the new path in its JSON output.
2. Add `modules/home/ai/plugins/package.json` with the `semantic-release-monorepo` + `semantic-release-major-tag` (18-entry `customTags`) release config.
3. Verify via the hermetic `release-rehearsal` check (`checks.<system>.release-rehearsal`, which runs the same release program against stubs and cannot push tags) that the new package is discovered and semantic-release completes its analysis. Until that check exists, the local equivalent is `nix run .#release -- modules/home/ai/plugins -- --dry-run` (semantic-release's own dry run with the production plugins; needs `GITHUB_TOKEN`).
4. Merge to `main`; the live `release-packages` effect cuts the first real `@vanixiets/plugins-v1.0.0` tag plus 18 aliases on the next qualifying commit under `modules/home/ai/plugins/**`.
5. Add the tag-triggered relock-notify GH Actions workflow; verify it fires on the tag pushed in step 4 (or a subsequent test tag) and opens a PR.
6. Repoint the 18 `dependencies.apm` entries in the root `apm.yml` from `#main` to `#<group>-v1.0.0`, run `just agents-relock`, and verify `apm outdated` now reports `up-to-date`/`outdated` (never `unknown`) for all 18.
7. Rollback: each step is independently revertible — removing `modules/home/ai/plugins/package.json` and reverting `list-packages-json.sh` stops future releases without touching already-cut tags; reverting the `apm.yml` ref repointing returns the 18 deps to `#main` without needing a lockfile schema migration, since `apm.lock.yaml` always stores a resolved SHA regardless of the manifest ref's form.

## Open Questions

1. Is the root `package.json`'s own `release` block (`v${major}`/`v${major}.${minor}` via `semantic-release-major-tag`) actually invoked by anything today? `list-packages-json.sh` only discovers `packages/<name>/package.json`, and the root package.json sits outside `packages/`. If it is genuinely dead configuration, that changes nothing about D3's namespace-collision reasoning (accepted either way) but is worth confirming so a future contributor does not assume it fires. Experiment: instrument or read `release-packages` effect logs for a recent main-branch run and check whether `packages discovered:` (the effect's own echoed JSON, `release-packages.nix:224-225`) ever lists a root-scoped entry; absence across several runs would confirm it is dead.
2. Does a GitHub Actions `on.push.tags` glob actually fire for a tag ref containing both `@` and `/` (e.g. `@vanixiets/plugins-v1.0.0`)? The `@vanixiets/docs-v*` tags prove such refs can exist and be pushed in this repo, but no existing GH Actions workflow triggers on `push.tags` for them (the release pipeline that creates them is entirely hercules-ci-driven, not GH-Actions-triggered), so this specific trigger shape is unverified. Experiment: push a throwaway tag matching the glob (e.g. `@vanixiets/plugins-v0.0.0-test`) to a scratch ref and confirm the workflow run appears in the Actions tab before relying on it for the real release-triggered case.
