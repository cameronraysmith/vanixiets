## ADDED Requirements

### Requirement: Each fact about a plugin group is authored once

Each plugin group directory under `modules/home/ai/plugins/<group>/` SHALL contain `apm.yml` and its `.apm/` content and no other manifest.

The group's `apm.yml` SHALL be the only authored place for its name, description and version; the directory tree for its source path and whether it has skills; the root `marketplace:` block for the owner and the published list (names and sources, no versions).

**Relies on**: A213, A215.

#### Trust boundary

Evaluation and the generator's build establish that the authored facts are consistent with each other and with the directory tree. They do not establish that a description is accurate or that a group's grouping makes sense.

#### Scenario: A per-group manifest reappears

- **WHEN** a file named `plugin.json`, or a `.claude-plugin/` directory, is committed inside a group directory
- **THEN** evaluation of the marketplace generator fails naming the file, before any build starts

#### Scenario: The published list and the tree disagree

- **WHEN** a group directory exists that the root `marketplace.packages` list does not name, or the list names a source that is not a group directory, or a group's `apm.yml` `name` differs from its directory name
- **THEN** the marketplace generator's build fails naming the group

---

### Requirement: Both marketplace files are generated from the authored facts and committed unchanged

One derivation SHALL generate `.github/plugin/marketplace.json` (apm's Copilot profile, every published group) and `.claude-plugin/marketplace.json` (every published group that contains skills; each entry with `skills: ["./.apm/skills"]`, `strict: false` and no `version`).

**Mechanism**: the generator runs `apm pack --offline` over a private copy of the root manifest without its `dependencies:` and `compilation:` blocks, then one jq filter for the Claude file, which also gives the marketplace a description.

A check on `x86_64-linux` SHALL fail when either committed file differs from the generated one, and a just recipe SHALL write the generated files into the tree.

**Relies on**: A215, A216.

#### Trust boundary

The check establishes that the committed files are what the pinned apm and the filter produce from the committed manifests. It does not establish that a newer apm would produce the same files, or that apm and Claude accept them; the Claude install check and the offline consumer check cover acceptance for the pinned versions.

#### Scenario: A description changes without regenerating

- **WHEN** a group's `apm.yml` description is edited and the marketplace files are not regenerated
- **THEN** the drift check fails, printing the difference

#### Scenario: An apm bump changes the generated bytes

- **WHEN** an `llm-agents` bump moves apm to a release whose marketplace mapper writes different JSON
- **THEN** the drift check fails until the files are regenerated and the difference is reviewed

---

### Requirement: Claude Code installs every Claude entry with exactly its group's skills

A check on `x86_64-linux` SHALL, offline and with an isolated Claude configuration directory, run `claude plugin validate` on the repository's marketplace, add it as a directory marketplace, install every entry, and compare each installed plugin's skill names with the children of its group's `.apm/skills/`, failing on any difference.

**Relies on**: A217.

#### Trust boundary

The check establishes what the pinned Claude Code does with the committed marketplace from a local directory. It does not establish the desktop app's behaviour (A218), the behaviour of a GitHub-sourced marketplace, or that skills are offered to a model in a session.

#### Scenario: An entry points at a missing directory

- **WHEN** a Claude entry's `source` names a directory that does not exist
- **THEN** the install step fails although `claude plugin validate` passes

#### Scenario: An entry loses its skills path

- **WHEN** a Claude entry carries no `skills` field
- **THEN** the plugin installs with no skills and the check fails naming the group

---

### Requirement: An offline apm consumer installs from a served copy of the repository

A check on `x86_64-linux` SHALL serve a bare git repository built from the committed marketplace files and group directories, rewrite an `https://` repository URL to it with `url.insteadOf`, register it with `apm marketplace add`, install every published group that declares no remote dependency, and compare each installed first-party skill byte for byte with its source.

**Remote run**: `just agents-marketplace-remote` runs the existing flake app, `nix run .#apm-marketplace-validate -- --remote`, against the forge's main branch, outside the sandbox, for the groups with remote dependencies and the real forge route; it is not a gate, and a nixbot effect is its later home.

**Relies on**: A213, A216.

#### Trust boundary

The offline check establishes apm's handling of the committed files over a generic git host. It does not establish GitHub-specific resolution or the remote dependencies' availability; the networked recipe samples those when it is run, and is not a gate.

#### Scenario: A published source path is wrong

- **WHEN** a `marketplace.packages` source names a path that is not served
- **THEN** the offline consumer check fails at that group's install

---

### Requirement: The composed trees are compared with their sources and recorded hashes

The composition's build SHALL fail unless each skill directory under `.claude/skills` and `.agents/skills` is named in the committed skill index; each first-party skill directory is byte-identical to its `.apm/skills/<name>` source; each remote skill directory's `nix hash path` equals the hash the committed index records for it; and the two trees are identical.

**Relies on**: A136, A137, A139, A213.

#### Trust boundary

The build establishes the trees' content for the pinned apm on the building system. It does not establish that a remote skill's recorded hash is the right content; that is reviewed when the index is regenerated after a ref or apm change.

#### Scenario: An apm bump changes a remote skill

- **WHEN** an apm release adds, removes or rewrites a file inside a remote skill directory
- **THEN** the composition fails naming the skill and its recorded and actual hashes

#### Scenario: An apm bump rewrites a first-party skill

- **WHEN** an apm release rewrites a link or drops a file in a deployed first-party skill
- **THEN** the composition fails naming the skill and printing the difference

---

### Requirement: The composition installs without frozen mode and leaves no installation id

The composition SHALL pass `--no-frozen` to `apm install` and SHALL remove `.apm-local/installation` from its output.

#### Scenario: A CI variable reaches the builder

- **WHEN** `CI=true` is set in the composition's build environment
- **THEN** the build still succeeds, because the install is explicitly not frozen

#### Scenario: Two builds of one derivation are compared

- **WHEN** the composition is rebuilt with `nix build --rebuild`
- **THEN** no difference is reported

---

### Requirement: Group discovery is computed once

Which group directories exist and which contain skills SHALL be computed once, at evaluation time without import-from-derivation, and shared by the composition, the dependency download, home-manager and the marketplace generator.

#### Scenario: A group of skills is added

- **WHEN** a new group directory with `.apm/skills/` is committed and listed in the root `marketplace.packages`
- **THEN** the composition, the dependency download, home-manager and both marketplace files include it with no other edit
