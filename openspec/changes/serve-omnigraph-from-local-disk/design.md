## Context

magnetite runs `omnigraph-server` 0.16.0 over the cluster root `s3://sciexp/omnigraph/clusters/cookbooks-f17`, serving ten example graphs, one per cookbook of the pinned `omnigraph-cookbooks`, each seeded once by `omnigraph-seed-<graph>` after the create-once bootstrap made the root (`modules/machines/nixos/magnetite/default.nix`, `services.omnigraph`; `modules/nixos/omnigraph.nix`; `modules/lib/omnigraph-bootstrap.nix`).
The bucket `sciexp` is declared with `location = "enam"` (`modules/terranix/cloudflare.nix`); magnetite is a Hetzner CX53 in fsn1 (`modules/lib/cloud-machines.nix`).
A start takes about 4 min 50 s to open the ten graphs; the root took about 26 min to create.
The R2 settings are `s3.endpointUrl`, `s3.region = "auto"`, the `omnigraph-r2` generator's `EnvironmentFile`, and `OMNIGRAPH_CLUSTER_LEASE_SECONDS = "120"`.

What the omnigraph module already does for a local root:
- `storageUri` may be a plain path or `file://`; with the bootstrap on, an assertion requires it beneath `/var/lib/omnigraph`, the units' `StateDirectory`, because every unit runs with `ProtectSystem=strict` and `DynamicUser` and has no `ReadWritePaths`.
- The bootstrap creates a missing local root directory and keeps its markers as files in `<parent>/_omnigraph-markers/`.
- `vmTests.x86_64-linux.omnigraph-seed` serves `/var/lib/omnigraph/clusters/test` with magnetite's graphs and policies.
- The server unit's `ExecStartPre` assembles the bearer tokens file from the tokens file and each seed actor's token; `ExecStartPost` is the readiness probe (`modules/lib/omnigraph-readiness.nix`); `Restart=on-failure` with a start limit sized from the readiness timeout.
- The sandbox includes `ProtectProc=invisible`, `ProcSubset=pid` and `PrivateUsers=true`.

On magnetite, `/var/lib/omnigraph` is a symlink to `private/omnigraph`, root-owned, dated Aug 6 (observed 2026-11-26); `/var/lib/private` is `0700 root`.
Pool `zroot` holds 188 GiB with 111 GiB free; datasets created by hand on the installed host are declared in `disko.nix` for a reinstall and their properties are enforced by `zfs-set-*` and `zfs-assert-*` oneshots in `default.nix` (`root/greptimedb`, `root/postgresql-dumps`).
`services.zfs.autoSnapshot` keeps hourly 4, daily 3, weekly 1.

What the fleet already has that this change reuses:
- `modules/nixos/postgresql-backup.nix`: restic to a dedicated R2 bucket under the host's name, generated restic password, prompted R2 keys, a success stamp in `ExecStartPost`, a minutely publisher into the one textfile directory (`vanixiets.nodeExporter.textfileWriters`), `nodeExporterKeep`, and `PostgresqlBackupStale` at 36 h; its job and timer naming a zone, as `observability-notify` asserts for notified units.
- `modules/nixos/fleet-alert/rules.nix` with promtool cases, threshold mutants, fixture series and fire-and-resolve legs in `modules/checks/fleet-alert.nix`.
- Perses views provisioned from `modules/nixos/perses/resources/`, each placed in `queryChecked` or `notQueryChecked` in `modules/vm-tests/perses-greptimedb.nix`, linted by `checks.x86_64-linux.perses-lint`.
- The filesystem scraper covers every `fileSystems` entry of type `zfs`, so a dataset declared in disko falls under `FilesystemFillingWarn` and `FilesystemFull` without a rule change.

A separate change, in flight, fixes the collector's systemd allow-list entry (`omnigraph.service` on trunk, `schema.nix:30`) to `omnigraph-server.service` and adds `omnigraph-server` to magnetite's `notifiedUnits`.
This change assumes that lands first or alongside, and does not edit those two lines.

The evidence is nine research reports of 2026-11-26 and the operator's decisions recorded in `brainstorm.md`; the key one is a crash probe of a local root with the packaged 0.16.0 binary.

Stakeholders: the operator, who restores, holds the secrets and pays for R2; agents and people on pyrite and the Macs who query the graphs through cinnabar's fronts.

## Goals / Non-Goals

**Goals:**
- Watch the server that runs today, on R2, before anything moves.
- Serve magnetite's graphs from its own disk, with R2 still selectable per host.
- Restart after a crash without a person when, and only when, nothing else can hold the root.
- An off-host copy every night, restorable to identical answers, with an alert when it is overdue.
- Prove crash, refusal and restore in a runtime test before the switch.

**Non-Goals:**
- Copying `cookbooks-f17` from R2 to disk: the graphs are example data, seeded fresh.
- Trace export, a JSON log receiver, scheduled `omnigraph cleanup` (D11).
- Turning on `omnigraph-optimize`, or served optimize.
- The collector's unit name and the server's failure notice (separate change).
- Any client-side change: the URL stays.
- Hetzner Object Storage, a self-hosted S3 server, or a new R2 location for the graph data.

## Decisions

### D1: The graph data lives on a dataset of its own on magnetite's disk
- **Choice**: dataset `zroot/root/omnigraph`, `quota=20G`, auto-snapshot inherited (on), mounted at `/var/lib/omnigraph`, which is the omnigraph units' state directory itself. The root is `/var/lib/omnigraph/clusters/cookbooks-f17`; its bootstrap markers sit in `clusters/_omnigraph-markers/`, on the same dataset, so one snapshot holds the root and its markers together.
- **Rationale**: OmniGraph allows one writer and no replicas (A231), so storage local to the one writer loses nothing; Lance ranks local NVMe fastest; the quota keeps the graph data from starving the pool. The dataset can be the state directory because the omnigraph units run as a static user (D13), for which `/var/lib/omnigraph` is a plain directory that systemd hands to that user, not a `DynamicUser`'s symlink into `/var/lib/private` (A241).
- **Alternatives considered**: Hetzner Object Storage (conditional writes undocumented on unversioned buckets, HDD, its FAQ advises against this workload; A237); a new R2 bucket in western Europe (still a network round trip per request, and R2's latency is unmeasured from fsn1); a self-hosted S3 server on the same disk (a second service to run for no gain over the filesystem); a dataset at `/var/lib/private/omnigraph/clusters` below a `DynamicUser` state directory, and the dataset as a `DynamicUser` state directory (both set aside, see the decision record in D13).
- **Boundary**: source versus delivered: disko declares the dataset only for a reinstall; on the installed host the operator creates it once (D12, tasks 3.1).

### D2: The new root is created and seeded by the existing bootstrap
- **Choice**: no data migration. With the root pointed at the empty local path, `omnigraph-cluster-bootstrap` finds no state and no marker, creates the directory, writes seed-pending markers, applies, and the seed units load each cookbook's seed once the server serves.
- **Rationale**: the ten graphs are example data whose seeds are pinned; a fresh root is the path the module already proves.
- **Alternatives considered**: `rclone` or `aws s3 sync` of the live R2 root (a copy of a live root is not safe, A234, and stopping the server for a 26-minute download buys example data).

### D3: One host setting selects disk or R2 for the same root name
- **Choice**: `flake.lib.omnigraphClusterRoots` gains `localDirectory = "/var/lib/omnigraph/clusters"` and `uriIn = store: root:` returning `"${localDirectory}/${root}"` for `"local"` and the existing `s3://` URI for `"r2"`; `rootOf` also recognises a local URI. magnetite's module declares the internal option `vanixiets.omnigraphRootStore` (`"local"` or `"r2"`), sets it, and derives `storageUri` from it; `s3`, `environmentFile` and `OMNIGRAPH_CLUSTER_LEASE_SECONDS` are set only for `"r2"`. The `omnigraph-r2` generator, the lifecycle rules, `retired`, `rollback` and `checks.omnigraph-retired-roots` are unchanged. Local-only behaviour (D4, D5, D14, the mount requirement and the wrapper's `runuser` of D13, the dataset series in D6) keys off the URI being a plain path, which the module already classifies.
  Settled in implementation (2026-11-26): the setting is an option, not the `let` value this decision first named, because `checks.x86_64-linux.omnigraph-retired-roots` evaluates magnetite on the other store through `extendModules`, and a `let` value cannot be overridden from outside the module.
- **Rationale**: the root name already records the storage format; the same name in both places keeps the format window and the retired-roots logic one concept. Switching back is one value; R2's root is what it was when the host left it, and the R2 markers make the bootstrap a no-op there. The units run as the same static user on both stores (D13), so switching changes no state directory, and the dataset may stay mounted.
- **Alternatives considered**: a `services.omnigraph` option naming R2 (couples the generic module to one provider); deleting the R2 settings (makes the way back a revert of several hunks).

### D4: The server's own start clears a crashed server's lock, and nothing else does
- **Choice**: `flake.lib.omnigraphLockRecovery` (`modules/lib/omnigraph-lock-recovery.nix`) builds a program that the server unit runs as its first `ExecStartPre`, with the `+` prefix, only when the root is local. It reads `<root>/__cluster/lock.json` and decides by the first matching row below. Its `omnigraph cluster status` and `force-unlock` run as the static user `omnigraph` through `runuser` (its `runAs` argument, D13), so an unlock leaves no file owned by root. The manual steps it prints name `<cli>`: `omnigraph-cluster` where `services.omnigraph.cluster.enable` is set, as on magnetite, and `omnigraph --target <root> cluster` otherwise.

  | Row | Condition | Verdict | Reason printed |
  |---|---|---|---|
  | 1 | no `lock.json` | exit 0, nothing run | none |
  | 2 | `<proc>` does not list; a process with a non-empty command line has an unreadable command line or `exe` link; a process row 3 must judge by owner has an unreadable `status`; or `writerUser` (`omnigraph`) does not resolve to a uid. A process with an empty command line, a kernel thread or a zombie, is skipped | refuse | `the process table <proc> cannot be listed`, `the command line of pid <pid> cannot be read`, `the executable of pid <pid> (<argv>) cannot be read`, `the owner of pid <pid> (<argv>) cannot be read`, or `the user omnigraph does not exist, so the processes that may write the root cannot be told apart`; manual: check `<proc>`, or confirm with `ps -o pid,user,args -p <pid>` that the process does not use the root, then `systemctl restart omnigraph-server`; for the user, `<cli> force-unlock <lock_id>` once no omnigraph process runs against the root |
  | 3 | a process whose executable is named `omnigraph` or `omnigraph-server` and either lies under `/nix/store/*-omnigraph-*/bin/` (any version, ` (deleted)` included) or runs as root or `omnigraph` by any of its real, effective, saved or file-system uids, has an argument naming the root as `/var/lib/omnigraph/…` | refuse | `an omnigraph process has the root open (pid <pid>: <argv>)`; manual: wait for it or stop it, then `systemctl restart omnigraph-server` |
  | 4 | the record is not version 1 with a string `lock_id` (`[0-9A-Za-z]+`), `operation` (`[a-z_]+`), an RFC 3339 `created_at` and a positive integer `pid` | refuse | `the record is not the shape omnigraph writes for a held lock (…)`; manual: read the record and `<cli> status --json`, then `<cli> force-unlock <lock_id>` once no omnigraph process runs against the root |
  | 5 | `created_at` does not parse as a date | refuse | `the record's created_at (<value>) is not a date`; manual as row 4 with the record's id |
  | 6 | `cluster status --json` fails | refuse | `omnigraph cluster status failed, so the record's lock <id> cannot be confirmed as the cluster's`; manual as row 5 |
  | 7 | `cluster status --json` reports another `lock_id`, or none | refuse | `the record names lock <id> but omnigraph cluster status reports <other>, so the lock changed while it was read`; manual: `systemctl restart omnigraph-server` to read it again, and if it persists compare the record with `<cli> status --json` |
  | 8 | `operation` is not `serve` | refuse | `lock <id> was taken by a direct <operation> writer (pid <pid>, <created_at>), whose interrupted work needs its own recovery`; manual: find the deployment with `<cli> status --json`, then `<cli> force-unlock <id>` and `<cli> apply --deployment-id <deployment_id> --writers-stopped --json`; for a writer other than an apply, confirm it stopped and `<cli> force-unlock <id>` |
  | 9 | `<proc>/stat` cannot be read or its `btime` is not an integer | refuse | `the boot time in <proc>/stat cannot be read, so whether lock <id> was taken in this boot cannot be told`; manual as row 11 |
  | 10 | `<proc>/<pid>` runs an executable named `omnigraph` or `omnigraph-server`, from any path, owner or argument list, whatever the boot time | refuse | `pid <pid>, which lock <id> names, is running <exe> (<argv>), so the lock may be that server's whatever the boot time says`; manual: confirm with `ps -o pid,args -p <pid>` whether it serves the root; if not, `<cli> force-unlock <id>` and `systemctl restart omnigraph-server`; if so, stop it and `systemctl restart omnigraph-server` |
  | 11 | `<proc>/<pid>` exists and `created_at` is not before `btime` | refuse | `lock <id> was taken in this boot (<created_at>) by pid <pid>, which is running`; manual: confirm with `ps -o pid,args -p <pid>` that it is not a server holding the root, then `<cli> force-unlock <id>` and `systemctl restart omnigraph-server` |
  | 12 | otherwise: the pid is gone, or the lock predates this boot and the pid now runs another program | `cluster force-unlock <id> --json`, which must report `"unlocked": true` | `omnigraph-server on <host> cleared the stale serve lock <id> of <root> (pid <pid>, taken <created_at>) and starts; lock recoveries on <host>: <n>` |

  Every refusal leaves `lock.json` unchanged, prints `omnigraph-lock-recovery: left <lock> in place: <reason>` and `omnigraph-lock-recovery: omnigraph-server stays stopped until the lock is cleared. <manual step>`, and exits 1; the start job fails, `Restart=on-failure` retries within the start limit, and the failure notice reports it. In row 12 a `force-unlock` that fails or does not report the lock removed exits 1 with `omnigraph cluster force-unlock <id> did not report the lock removed`; a removal adds one to the integer in `/var/lib/omnigraph-metrics/lock-recoveries` (0 when absent or unreadable) and posts the row's message at `Priority: low` with the title `omnigraph lock recovered on <host>` to `fleet-alerts` through `ntfy-send`, under a 30 s timeout whose failure does not fail the start.
- **Rationale**: a local lock is never taken over and `force-unlock` checks only the id (A232); without this, every crash needs a person. `+` is needed because the sandbox hides other users' processes (`ProtectProc=invisible`, `PrivateUsers`), and an `omnigraph` run by hand as root is such a process. A process table the program cannot read refuses rather than counting as no process, since an unlock is the one irreversible outcome. Row 3 counts an omnigraph package's executable from any version, and any executable of that name run by root or `omnigraph`, the users that can write the root; an executable of that name elsewhere run by another user cannot, and counting it would let any user keep the server from starting. Row 10 holds whatever `btime` says because a server the scan misses (a relative path, a named or default `--target`) would otherwise pass row 11 once the wall clock steps forward after its lock was taken: the boot time only excuses a pid that now runs another program. Running before the server starts, and only there, means no second unit can race the server's own start; the bootstrap and apply units are ordered before the server.
- **Alternatives considered**: a separate recovery unit (`Before=`/`Conflicts=` ordering to keep in step with the server's restarts, for nothing); trusting the pid alone (pids are reused, and the record carries no boot id); unlocking a non-`serve` lock (a direct writer's interrupted work needs its own recovery, not a bare unlock).
- **Boundary**: first-party program over a vendored binary's on-disk record; the record's meaning is A232 and is checked at each OmniGraph bump by the rehearsal and the runtime test.

### D5: Nightly backup from a ZFS snapshot to `sciexp-omnigraph-backup`
- **Choice**: `modules/nixos/omnigraph-backup.nix`, `vanixiets.omnigraphBackup.enable`, modelled on `postgresql-backup.nix`: `services.restic.backups.omnigraph` with repository `s3:<account endpoint>/sciexp-omnigraph-backup/<hostName>`, `s3.bucket-lookup=path`, `s3.region=auto`; `backupPrepareCommand` destroys any leftover `zroot/root/omnigraph@restic` and takes it anew; `paths = [ "/var/lib/omnigraph/.zfs/snapshot/restic" ]`, a fixed path so restic finds its parent snapshot; `backupCleanupCommand` destroys the snapshot; `--keep-daily 7 --keep-weekly 4 --keep-monthly 6 --group-by host`; `--read-data-subset=10%`; `OnCalendar = "*-*-* 03:30:00 UTC"`, `RandomizedDelaySec = "15m"`, `Persistent = true`. Generators `omnigraph-backup-r2` (prompted, hidden) and `omnigraph-backup-restic` (generated). The success stamp `vanixiets_omnigraph_backup_last_success_timestamp_seconds` and its minutely publisher `omnigraph-backup-metric` follow the PostgreSQL module. terranix declares `cloudflare_r2_bucket.sciexp-omnigraph-backup` with `prevent_destroy` and no lifecycle rule. The module asserts that the root is local, that the job's only path is the snapshot directory, that the job, `omnigraph-backup-metric` and `zfs-set-root-omnigraph-quota` are in the host's `notifiedUnits`, and that the textfile collector keeps the stamp. A restore stops `restic-backups-omnigraph.timer` with the server, so that no backup of a half-restored dataset can make the daily prune drop that day's good backup, restores the snapshot it chose rather than `latest`, takes `zroot/root/omnigraph@pre-restore` before emptying the dataset and destroys it once the restored server answers as the backup did, and ends with `chown -R omnigraph:omnigraph` of the dataset and the timer started again. The backup records every file of the dataset with the numeric uid and gid of `omnigraph` on the host it was taken on, and restic restores those numbers (the runtime test checks both), so the `chown` matters on a restoring host where the static user has another uid (D13).
- **Rationale**: a snapshot is an instant image (A235); a live copy is not safe (A234). 03:30 keeps the job apart from the PostgreSQL job's memory at 02:30.
- **Alternatives considered**: `zfs send` to a remote pool (no second pool exists); stopping the server for a copy (an outage every night); `omnigraph export` (logical, per branch, and loses the cluster ledger).
- **Boundary**: first-party module over nixpkgs' restic module, as the PostgreSQL backup.

### D6: A minutely probe publishes the server's state to the textfile collector
- **Choice**: `modules/nixos/omnigraph-probe.nix`, on with `services.omnigraph.enable` on a host with the textfile collector; `omnigraph-probe.service` (oneshot, `MemoryMax=32M`) and a 60 s timer, writer `omnigraph`. Series, each added to `nodeExporterKeep`:
  - `vanixiets_omnigraph_ready` (1 only when `/readyz` answers `ready: true`; 0 when it answers otherwise or not at all);
  - `vanixiets_omnigraph_graphs{state="served|ready|loading|blocked"}`;
  - `vanixiets_omnigraph_start_to_ready_seconds` (from `omnigraph-server`'s `ExecMainStartTimestampMonotonic` and `ActiveEnterTimestampMonotonic`);
  - with the monitor token: `vanixiets_omnigraph_graph_entities{graph}` (sum of `entity_count` of `GET /graphs/{id}/snapshot`), `vanixiets_omnigraph_graph_manifest_version{graph}`, `vanixiets_omnigraph_graph_storage_format{graph}`;
  - on a local root: `vanixiets_omnigraph_dataset_used_bytes`, `vanixiets_omnigraph_dataset_quota_bytes`, `vanixiets_omnigraph_dataset_snapshots`, and `vanixiets_omnigraph_lock_recoveries_total` from D4's counter.
  The file is written then renamed; a failed per-graph read omits that graph's series and leaves the readiness series.
  Settled in implementation: the probe runs as node_exporter's user, not a `DynamicUser`, because a `DynamicUser`'s files sit under `/run/private`, which node_exporter cannot traverse (as `magnetite-memory-budget.nix` found). The per-graph reads list the graphs with `GET /graphs` (action `graph_list`) and read the snapshot of each graph whose `state` is `ready`; both routes refuse a request without the `Omnigraph-Http-Api` header, whose value the probe takes from the same header on the `/readyz` answer, which the server sets on every response. A ZFS series names the dataset mounted at the deepest of the root's parent directory and its ancestors below `/var/lib`, so a dataset at `/var/lib/omnigraph` (D1) is found; with none the dataset series are left out. `vanixiets_omnigraph_lock_recoveries_total` is 0 while D4's counter file is absent. The probe is on only where node_exporter runs, so a VM serving omnigraph without it, as `vmTests.x86_64-linux.omnigraph-seed`, gets no probe.
  Settled in implementation (2026-11-26): with the monitor token the probe also writes `vanixiets_omnigraph_graph_reads_ok`, 1 when `GET /graphs` and every ready graph's snapshot read succeeded and 0 otherwise (the server down included), and logs one line per failed request, `omnigraph-probe: GET <path> answered HTTP <status>` (`000` for no HTTP answer, or `answered HTTP 200 with an unreadable body`); the unit still exits 0. The gauge is in `nodeExporterKeep` and on the view (D9). Reason: the first deploy of the probe found `GET /graphs` answering 403 to `monitor` on the R2 root, which had not been applied with its grant, while the probe logged nothing and the per-graph series were simply absent (`logs/agent-reports-20261126/DeployMagnetite-probe.md`, check 3).
- **Rationale**: OmniGraph has no metrics endpoint (A238); the textfile collector is the fleet's pattern; `HostProbeStale` already reports a probe that stops.
- **Alternatives considered**: scraping `/metrics` (none exists); log-derived counters (D11).

### D7: A read-only `monitor` actor with a generated token
- **Choice**: generator `omnigraph-monitor-token` on magnetite; `services.omnigraph` gains `extraBearerTokenFiles` (actor name to token file), merged by the existing `ExecStartPre` exactly as seed tokens are, refusing an actor already named; the probe receives the same file by `LoadCredential`. `server.policy.yaml` grants group `monitors: [monitor]` `graph_list`; `examples.policy.yaml` grants it `read` and nothing else. `checks.omnigraph-cluster-actor-policy` gains allow cases for those and deny cases for `change`, `export`, `schema_apply` and `maintain`, and for `config_manage` on the `cluster` bundle. An extra actor that is also a seed actor fails evaluation, as two seed actors with different token files do.
- **Rationale**: per-graph counts need a token; a separate actor keeps `admin`'s token off a minutely timer.
- **Alternatives considered**: the admin token (broad write access in a probe); the seeder (`change` on `main`).
- **Boundary**: the policy reaches a root only through an apply; the new local root gets it at creation, the R2 root only through a hand-run apply (Open Questions 2).

### D8: Two rules
- **Choice**: in `rules.nix`, `OmnigraphNotServing`: `vanixiets_omnigraph_ready == 0 or vanixiets_omnigraph_graphs{state="blocked"} > 0`, `for = "5m"`, warning; `OmnigraphBackupStale`: `time() - vanixiets_omnigraph_backup_last_success_timestamp_seconds > 129600`, `for = "10m"`, warning. Each gets a promtool case with a threshold mutant, a fixture series in `fleet-alert/fixtures/series.json`, and a fire-and-resolve leg in `legs`. The annotations name the runbook.
- **Rationale**: the two failure classes a person must act on; the 36 h window is the PostgreSQL backup's.
- **Alternatives considered**: a lock-recovery rule (D4 posts its own notice; recoveries are expected events, not failures).

### D9: A Perses view and docs
- **Choice**: `modules/nixos/perses/resources/dashboard-omnigraph.json` in project `fleet`, datasource `greptimedb-promql`, panels: readiness and graph states, start-to-ready seconds, entities per graph, manifest version and format per graph, whether the per-graph reads succeeded, dataset used against quota, snapshot count, backup age, lock recoveries, `omnigraph-server` memory. Placed in `queryChecked`. Docs: `fleet-observability.md`'s alert table, and a runbook `packages/docs/src/content/docs/development/operations/omnigraph.md` beside `postgresql-backup.md`, begun with the monitoring and completed with recovery, restore and switching back.

### D10: A runtime test with ZFS in the VM
- **Choice**: `vmTests.x86_64-linux.omnigraph-local-root`, class `medium` in `testSizes.vmTests` (its script took 80.75, 81.36 and 79.84 s in three runs on pyrite, over the small limit of 60 s); one node with `boot.supportedFilesystems = [ "zfs" ]`, a second virtual disk holding a pool created root-owned at first boot, the dataset at `/var/lib/omnigraph` declared through `virtualisation.fileSystems` (a test VM ignores `fileSystems`), the real omnigraph, probe and backup modules, two of magnetite's graphs, and a restic repository on a local path. Cases: the dataset is the state directory, holds the root and markers, and every file on it belongs to `omnigraph`; every unit and the root-invoked `omnigraph-cluster apply` write as `omnigraph`; `kill -9` of the server, restart with recovery, same counts and answer, counter 1; a held `omnigraph` direct writer on the root makes the start refuse with the reason and leaves `lock.json` byte for byte; a backup recording every file of the dataset with `omnigraph`'s uid and gid, then the runbook's restore (the timer and server stopped, `@pre-restore` taken, the dataset emptied, the chosen backup restored with its owners, `chown -R`, the unlock, the start, `@pre-restore` destroyed and the timer started), identical counts and answer; a reboot mounts the dataset before the units, and the server, bootstrap, apply and seed units each name `/var/lib/omnigraph/clusters` in `RequiresMountsFor`; the probe's series present. It runs no `omnigraph optimize` (D14). Run on pyrite.
  A second runtime test, `vmTests.x86_64-linux.omnigraph-state-directory-transitions` (class `medium`, about 65 s of script, three passing runs), holds the state-directory moves of D13 with RustFS on the node standing in for R2: a `DynamicUser` generation's symlink, the first static start on the bucket, a rollback to `DynamicUser`, the preparation of the dataset and a switch to the local root, a switch back to the bucket with the dataset mounted, and a rollback to `DynamicUser` with the dataset mounted and then unmounted. Neither test gates a pull request.
- **Rationale**: the recovery and restore act on real files and processes; only a VM shows them end to end.

### D11: No traces, no JSON log receiver, no scheduled cleanup
- **Choice**: none of the three.
- **Rationale**: OmniGraph's exporter trusts only public certificate authorities (A239) and the fleet's collector serves an internal one; the fatal log events end the server process, which the readiness rule and the failure notice already report; `cleanup` runs only with the server stopped (A240), which an unattended timer would turn into a nightly outage. At 20 GiB of quota against a few MB of data, growth is watched by the dataset series and the filesystem rules instead.

### D12: Three delivery commits and a gated rollout
- **Choice**: (1) monitoring of the running server; (2) local-root support with magnetite still on R2; (3) magnetite's switch. The operator's bucket apply, token, vars and dataset sit between (2) and (3).
- **Rationale**: each commit evaluates and deploys on its own; (2) keeps magnetite serving the same R2 root, and changes only the user its omnigraph units run as (D13, Transition).

### D13: Every omnigraph unit runs as the static user `omnigraph`
- **Choice**: `modules/nixos/omnigraph.nix` declares the system user and group `omnigraph` (`users.users.omnigraph.isSystemUser`, `cfg.user` and `cfg.group`) and runs every omnigraph unit (bootstrap, apply, seeds, server, optimize) under that user with `DynamicUser` left unset (systemd's default, off), on either store, keeping `StateDirectory = "omnigraph"` and the same sandboxing. Where `storageUri` is a local path, every unit also carries `RequiresMountsFor` on the root's parent, `/var/lib/omnigraph/clusters`, which requires the dataset's mount, and direct writers run as `omnigraph` too: the `omnigraph-cluster` wrapper, invoked as root, runs `omnigraph` through `runuser -u omnigraph`, as do the recovery's `cluster status` and `force-unlock` (D4); the bootstrap, apply and seed units already run as the unit user. A restore ends with `chown -R omnigraph:omnigraph /var/lib/omnigraph`.
- **Rationale**: one owner for every file on the dataset, whoever writes. systemd hands a root-owned state directory of a unit with a static user to that user at start (`setup_exec_directory` in systemd v262 `src/core/exec-invoke.c` chowns a non-private state directory recursively to the unit's uid; A241), so a freshly created dataset needs no hand `chown`. The same user on both stores means switching stores changes no unit's user and no state directory, so the way back to R2 is the one option value. The uid comes from NixOS's system-user allocation, which is stable on one host but may differ on another, hence the restore's `chown`.
- **Transition**: the first deploy of this commit moves magnetite's R2 server from `DynamicUser` to `omnigraph`. At the first start of an omnigraph unit, systemd finds `/var/lib/omnigraph` a symlink to `/var/lib/private/omnigraph`, removes the symlink and renames the private directory to `/var/lib/omnigraph` ("Found pre-existing private StateDirectory= directory /var/lib/private/omnigraph, migrating to /var/lib/omnigraph."); the server restarts under the new user and serves from the bucket. The directory stays owned by `65534:65534` on disk: for a static user's state directory owned by `nobody` on a filesystem that supports id-mapping, `setup_exec_directory` gives the unit an id-mapped mount instead of a `chown`. No step is needed before the deploy. Switching a host from a local root to R2 with the dataset still mounted at `/var/lib/omnigraph` starts and serves every unit. A generation from before this commit runs `DynamicUser` again: with a plain `/var/lib/omnigraph` systemd renames it into `/var/lib/private` ("Found pre-existing public StateDirectory= directory") and serves, and with the dataset mounted there every unit fails with `Failed to set up special execution directory in /var/lib: Device or resource busy` (status 238/STATE_DIRECTORY) until `zfs unmount zroot/root/omnigraph`. Evidence: `vmTests.x86_64-linux.omnigraph-state-directory-transitions`, with RustFS on the node standing in for R2 (`logs/cam127c-omnigraph-state-directory-transitions-t2-20261126-011446.log`).
- **Alternatives considered**: see the decision record below.
- **Decision record (2026-11-26)**: D1 first mounted the dataset at `/var/lib/private/omnigraph/clusters`, below the `DynamicUser` state directory. systemd 262 gives a `DynamicUser` unit an id-mapped mount of its state directory when that directory is owned by root or by `nobody`, and creating that mount fails while a dataset is mounted below it: every omnigraph unit failed at `NAMESPACE` with `Failed to create an id-mapped mount: Device or resource busy` (`setup_exec_directory` in `src/core/exec-invoke.c`, `src/core/namespace.c`; red run `logs/cam127b-local-root-red-20261126-003539.log`). Mounting the dataset as the `DynamicUser` state directory itself started in a prototype (`logs/cam127b-local-root-optA-20261126-003758.log`) and was set aside: behind the mapping the files are owned by `nobody` on disk, a direct writer run as root creates files the server cannot write, and the ownership a restore must give the files is unclear. Dropping `DynamicUser`, first rejected as larger than needed, is the choice above. It was first made for a local root only, keeping `DynamicUser` on R2; that was set aside the same day because switching from a local root back to R2 would then turn `DynamicUser` on again and make systemd rename the mounted `/var/lib/omnigraph` into `/var/lib/private`, which fails, so the way back would need the dataset unmounted first.

### D14: `omnigraph optimize` is not enabled on a local root
- **Choice**: an assertion in `modules/nixos/omnigraph.nix` fails evaluation when `services.omnigraph.optimize.enable` is set for a local `storageUri`, with a message saying that optimize leaves its admission lock behind on a local root, that the server's next start then meets a direct writer's lock which the recovery refuses to clear, and that the server stays down until `omnigraph-cluster force-unlock <LOCK_ID>`. Optimize on a local root is out of this change's scope; magnetite has the timer off.
- **Rationale**: in the runtime test, `omnigraph optimize --graph <first>` against the local root exited logging `cluster admission retained … use exact-ID cluster force-unlock`, and the unit's next graph then failed with `state_lock_held` (`logs/cam127b-local-root-static4-20261126-004816.log`; A242). The lock is a direct writer's, which D4 rightly refuses, so an enabled timer would turn each run into a server that cannot start.
- **Alternatives considered**: unlocking after each optimize run in the unit (a bare unlock of a direct writer's lock is what D4 refuses, and it would hide a writer that did not finish); served optimize (a Non-Goal of this change).

## Risks / Trade-offs

- [Risk] The disk is lost with magnetite. → Mitigation: nightly off-host copy (D5), recovery point at most 24 h plus margin; the graphs are example data and reseedable.
- [Risk] Recovery unlocks a lock a live writer holds. → Mitigation: refuse on a process table it cannot read, on any omnigraph process that may write the root naming it, on a non-`serve` lock, on an id mismatch, on a boot time it cannot read, on an omnigraph executable at the record's pid whatever the boot time, and on a live pid within the boot (D4); the rehearsal and the runtime test hold each refusal.
- [Limit] A server in another pid namespace, such as a container, holding the root is not recognised by its pid: its record's pid is the namespace's, which on the host is absent or another program, so only the argument scan (D4 row 3) or, while some host process happens to hold that pid in the same boot, row 11 stops the unlock. The runbook says to serve and write the root only from the host.
- [Risk] A refused start leaves the server down. → Mitigation: the start fails visibly; `OmnigraphNotServing` and the failure notice report it; the reason names the manual command.
- [Risk] Files on the dataset end up owned by someone other than `omnigraph` (a restore from another host, an `omnigraph` run by hand as root), and the server cannot write them. → Mitigation: every unit, the `omnigraph-cluster` wrapper and the recovery run as `omnigraph` (D13); the restore ends with `chown -R omnigraph:omnigraph /var/lib/omnigraph`; the runbook says to run direct writers only through the wrapper; the runtime test checks that no file on the dataset has another owner after each step.
- [Risk] Rolling magnetite back to a generation from before this commit fails every omnigraph unit's start while the dataset is mounted at `/var/lib/omnigraph`: that generation runs `DynamicUser`, and systemd's rename of a plain `/var/lib/omnigraph` into `/var/lib/private` fails on the mountpoint with status 238/STATE_DIRECTORY (D13, Transition; observed in `vmTests.x86_64-linux.omnigraph-state-directory-transitions`). → Mitigation: the migration plan's rollback and the runbook unmount the dataset first; switching stores needs no such step.
- [Risk] `omnigraph optimize` on a local root leaves its admission lock behind, and the server then stays down (A242). → Mitigation: an assertion forbids the optimize timer on a local root (D14).
- [Risk] `OmnigraphNotServing` fires during an R2 start (about 4 min 50 s, close to the 5 min window). → Mitigation: accepted for the days between commits (1) and (3); on disk a start takes seconds.
- [Limit] The optimize assertion of D14 has no test that gates a pull request: reading any of magnetite's assertions from a check forces all of them, and a version of `checks.x86_64-linux.omnigraph-retired-roots` that read them took 38.6 s at 2.5 GiB peak to evaluate, against 2.1 s at 0.32 GiB for the check on trunk, on every pull request (`logs/cam127c-retired-roots-evalcost-20261126-012646.log`), so the check reads none of them. Its evidence is three manual evaluations of magnetite with and without the option.
- [Limit] The probe's behaviour (its series, the per-graph reads and `vanixiets_omnigraph_graph_reads_ok`) is covered only by the runtime test `vmTests.x86_64-linux.omnigraph-local-root`, which does not gate pull requests; a pull request is gated only by the module's evaluation and its keep-list assertion.
- [Risk] OmniGraph changes its lock record in a later release. → Mitigation: the program refuses a record it cannot read; the rehearsal runs against the packaged binary's record at every bump.
- [Trade-off] Switching back to R2 loses local writes. → Accepted: example data; the runbook says so.
- [Trade-off] Local snapshots and the off-host copy both hold the restic snapshot only briefly; auto-snapshots pin old Lance files for up to a week. → Accepted within 20 GiB.
