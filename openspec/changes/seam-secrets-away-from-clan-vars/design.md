### Requirements and the world they rest on

| Req | Statement (behavioral, `secret-consumption-seam`) | Rests on | Breaks if it fails | Discharged by |
|---|---|---|---|---|
| R1 | A feature names the secrets it owns and uses without naming the secret backend | — | a backend swap edits every feature | D1, D2, D6, D9 |
| R2 | Moving a feature behind the seam leaves every delivered secret's location, recipe, custody and restart behaviour unchanged, and every host, home, check and runtime test unchanged except declared differences | A361, A362, A363 | a host loses a secret or restarts a unit at deploy | D3, D10, D11 |
| R3 | A home configuration receives the secrets it reads from its host without reading the host's secret backend | A362 | a home breaks when the backend changes | D5 |
| R4 | Replacing the secret backend changes only the seam and the named judges that pin the backend | A360, A364 | a later swap is a fleet-wide rewrite | D7, D8, D9 |
| R5 | A runtime test that runs a secret's recipe runs the recipe production uses | — | a test passes on a recipe production never runs | D8 |
| R6 | Each delivery step is shippable alone and leaves no secret half moved | A363 | a revert leaves a generator written twice | D10 |

### Stakeholders

The operator, who reviews thirteen pull requests and deploys nothing (no host changes). The features' authors, who will declare secrets through one option. The later den or backend-replacement change, which inherits a two-file swap. The predecessor compose-hosts-from-cohesive-aspects, which rewrites the files most of these steps touch.

## Goals / Non-Goals

**Goals:**
- One option, `vanixiets.secrets.<name>`, on the NixOS and nix-darwin classes, through which every first-party module declares and reads secrets.
- One secrets module, `modules/system/secrets.nix`, the only first-party module that names `clan.core.vars` outside the named judges (D8). With `modules/lib/vars.nix` (the committed-store half) it is the seam.
- Homes read a host-provided view, never `osConfig.clan`.
- Every NixOS, darwin and home toplevel and every runtime test keeps its drvPath at every step; the checks that change are named in each step's allow-list.
- A structural check that fails when a module outside the seam names the backend, arriving as a shrinking allow-list in the first step and as the full rule in the last.

**Non-Goals:**
- Replacing clan, renaming any generator or file, moving anything under `vars/`, or changing who can decrypt any secret.
- `clan.core.settings.*` reads (`machine.name`, `directory`, `domain`): host identity and location, not secrets. `vcs-signing.nix:22`'s machine-name read stays; a later den change owns host identity in homes.
- Reading committed public values, which `flake.lib.vars` already owns.
- Deploying anything: no host's configuration changes.

## Decisions

### D1: `vanixiets.secrets.<name>` is the only declaration and read interface

- **Choice**: `options.vanixiets.secrets = attrsOf (submodule secretModule)` on `flake.modules.nixos.secrets` and `flake.modules.darwin.secrets`, both defined in `modules/system/secrets.nix`. `<name>` is the generator name. A feature that owns a secret writes `vanixiets.secrets.<name> = { … }`; any module that needs it reads `config.vanixiets.secrets.<name>.files.<f>.path`.
- **Rationale**: one option keeps clan in one file. A typed submodule makes a misspelt field an evaluation error at the feature. Boundary: vendored-versus-first-party. The option is first-party; clan's generator interface is used through it, not patched.
- **Alternatives considered**: (a) a path option per feature like `notifyTokenFile`; every owner still writes `clan.core.vars`. (b) a `flake.lib` function from name to path; it cannot carry custody and must read `config.clan` wherever it is called.

### D2: the option carries the fields the fleet uses, with no pass-through

- **Choice**: writable fields, each `nullOr` with default `null` (lists default `[ ]`), so that only defined fields are written:
  - generator: `share`, `dependencies`, `validation`, `runtimeInputs`, `script`, `prompts.<p>.{description,type,persist}`, `prompts.<p>.display.{group,label,required,helperText}`;
  - file: `files.<f>.{secret,deploy,owner,group,mode,neededFor,restartUnits}`;
  - `provided : bool` (D4).

  Read-only fields: `files.<f>.{path,value,exists,placeholder}`, each `null` when no backend is evaluated (D3). The field list is the set used by the 34 declaring files on 2026-11-27 (`description` 228, `type` 183, `files` 99, `script` 86, `runtimeInputs` 53, `owner` 40, `group` 38, `mode` 28, `restartUnits` 25, `secret` 21, `prompts` 20, `persist` 17, `neededFor` 14, `share` 8, `dependencies` 4, `validation` 2, `deploy` 1 line hits), against clan's generator submodule (`modules/clan/export-modules/generic-generator.nix:79-325` in clan-core). `finalScript` is not exposed (D8).

  One more read-only field, on the entry: `resolved`, the generator as clan evaluated it, projected to the writable fields' names (`share`, `dependencies`, `validation`, `runtimeInputs`, `script`, `prompts.<p>.{description,type,persist,display}`, `files.<f>.{secret,deploy,owner,group,mode,neededFor,restartUnits}`), with clan's defaults applied and every file clan has; `null` without the backend. The writable fields hold only what modules defined, so a field no module set reads as `null` there: `nixos/r2-usage.nix:257` expects the `cloudflare-analytics` token's owner to be `root`, which only clan's default supplies. Judges of custody therefore read `resolved`, never the writable fields: `r2-usage.nix:257`, `darwin/otel-collector-agent.nix:557,568`, the custody assertions of `home/ai/omnigent/credentials.nix`, and `lib/{omnigent-fleet-obligations,commit-signing}.nix`. Its projection drops clan's own fields (`finalScript`, a file's `rel_dir` and `name`, a prompt's `name`). Measured on magnetite with a name-only entry for `cloudflare-analytics`: `resolved.files.token.owner` is `"root"` while the entry's `owner` is `null`, and the toplevel is unchanged (`logs/ssv-batch-resolved-probe-20261127-181748.log`).
- **Rationale**: answers proposal question 1. A pass-through attribute would put clan's vocabulary back into feature files. A field the fleet starts to need is a one-line seam edit, and the translation judge (D11) fails until it is added on both sides.
- **Alternatives considered**: a field-for-field mirror of clan's schema. It changes whenever clan's schema does and exposes fields no feature sets.

### D3: translation writes only defined fields, and only when clan is present

- **Choice**: `config = lib.optionalAttrs (options ? clan.core.vars) { clan.core.vars.generators = mapAttrs (_: toClan) (filterAttrs (_: s: !s.provided) cfg); }`, where `toClan` drops every `null` field and every empty list. Read-only fields are set from `config.clan.core.vars.generators.<name>.files.<f>` (`path`, `value`, `exists`) and `config.sops.placeholder."vars/${rel_dir}/${f}" or null` (`placeholder`, A361) when clan is present, and `null` otherwise. sops-nix defines a placeholder for each sops secret only on a host with `sops.templates`, so `placeholder` is `null` on a host without templates and for a file that is no sops secret, and a home's view, which carries it, evaluates on every host. The five `options ? clan.core.vars` guards leave their feature files and exist once here.

  The two omnigent host modules also define `sops.templates` under that guard (`nixos/omnigent-host.nix:468`, `darwin/omnigent-host.nix:540`). That option is sops-nix's, and the clan-free fixtures that import those modules (`checks/omnigent-workers.nix:200,333`, `vm-tests/omnigent-worker-isolation.nix:148-150`) do not import sops-nix; a definition under `mkIf false` for an option that does not exist still fails. The template definition therefore keeps a guard on the option it defines, `options ? sops.templates`, which holds exactly where `options ? clan.core.vars` holds today (every fleet host, through clan-core) and fails in those fixtures. The guard names `sops.templates`, not `sops`: `darwin/omnigent-host.nix:242` declares `sops.package` itself, so `options ? sops` holds in the darwin fixture, and with it `checks.aarch64-darwin.omnigent-worker-darwin` fails to evaluate. The generator definitions leave the guard.
- **Rationale**: clan's own defaults stay authoritative for every field a feature did not set, so the generator clan evaluates receives the same definitions as before (A363). Writing only defined fields is what keeps `mode`, `owner` and `neededFor` defaults identical. The guard answers proposal question 4: it is still needed, because clan-free fixtures import secret-owning modules, and it is now needed in one place. Boundary: source-versus-delivered. The translation decides what clan generates and installs; the drvPath diff shows the evaluated result is unchanged, not that clan installs the same file at runtime.
- **Alternatives considered**: the option sets its own defaults and always writes them. Equal values only for as long as the two sets of defaults agree, and every unset field would become a definition.

### D4: generators clan's own services declare are read as provided entries

- **Choice**: a module that reads a generator declared by a clan-core service declares `vanixiets.secrets.<name>.provided = true` and, by name only, each file it reads (`files.<f> = { }`). The secrets module translates nothing for it and fills those files' read-only fields from clan. Setting any writable field on a provided entry, at the generator or on a file, fails evaluation where clan is present, with a message naming the entry and each field set (`vanixiets.secrets.<name> is provided by the secret backend, so it cannot set <field>, …`): the generator is the clan service's, and the translation would drop the field. Two readers use it: `lib/host-keys.nix` (`openssh`) and cinnabar's `zt-dns` (`zerotier-network-zerotier`). Reading a file of a provided entry whose generator clan does not declare fails, with a message naming the entry (`vanixiets.secrets.<name> is provided, but the secret backend declares no generator <name>`). The files are declared by the reader, not filled from clan's generator, because the writable-field check reads a provided entry's files while clan's generator set is being computed, and filling them from that set would recurse.

  `lib/host-keys.nix`'s obligation tests whether the host has an `openssh` generator at all (`:42`) before comparing its value, so that a NixOS host without clan's sshd service, and the fixture `noOpensshGenerator`, report nothing. Once `assertionsModule` declares the provided entry on every NixOS host, `vanixiets.secrets ? openssh` is always true, and reading the value of an entry clan lacks fails. The presence test therefore reads the backend's own tree, `flake.lib.secretsBackend.generatorsOf hostConfig ? openssh` (D7), and the value reads the option. Its fixtures (`checks/host-key-obligations.nix:29,54`) supply both, so that check keeps a literal stub of clan's tree and joins D8's set as a literal fixture.
- **Conditional reader**: the `zerotier-network-zerotier` entry exists only if `machines/nixos/cinnabar/zt-dns.nix` exists at step 11's parent. migrate-mesh-to-tincr's open task 12.1 deletes that file together with the `zerotier` inventory instance. If that task has landed first, step 11 declares no provided entry for zerotier, this change's task 12.4 does not apply, and `lib/host-keys.nix` is D4's only reader. The reason is that a provided entry names a generator that some reader reads. With the reader and clan's generator both gone, the entry would fail on its first read.
- **Rationale**: the option's names are fixed by definitions and never computed from clan's tree, so declaring the generators from the option and reading paths back cannot recurse. Listing the clan-provided names statically at their readers keeps that property. Boundary: vendored-versus-first-party (A364).
- **Alternatives considered**: mirror every clan generator into the option automatically. The option's attribute names would then depend on clan's, which depend on the option's: infinite recursion.

### D5: homes read a view that hm-sops-bridge sets, on both classes

- **Choice**:
  - A home-manager module `flake.modules.homeManager.secrets`, also in `modules/system/secrets.nix`, declares a read-only-in-spirit `vanixiets.secrets` option in every home: an attribute set of `{ files.<f>.{path,placeholder} }`, default `{ }`.
  - `nixos/hm-sops-bridge.nix` gains, beside its age-key propagation, `home-manager.sharedModules = [ homeManager.secrets viewModule ]`, where `viewModule` sets each home's `vanixiets.secrets = view config.home.username`, and `view u` holds the host's entries with at least one file whose `owner` is `u`, projected to `{ files.<f>.{path,placeholder} }`. The view is set inside each home from its `home.username`, not by the host as `home-manager.users.<u>.vanixiets.secrets = view u`, because a host-level definition of `home-manager.users` derived from that option's own attribute names recurses. The view part does not depend on `hm-sops-bridge.users`.
  - The bridge file gains `flake.modules.darwin.hm-sops-bridge` with the view part only (darwin homes take their age key from `~/.config/sops/age/keys.txt`, `hm-sops-bridge.nix:11-13`), imported into `darwin.base`. The NixOS module is imported into `nixos.base` so every NixOS home gets the view. Both bridge modules carry the identity key `vanixiets/hm-sops-bridge` through `flake.lib.exportAs`.
  - Import depth. The module system collects imports breadth first (compose-hosts-from-cohesive-aspects' world assumption, measured there), so an import moved from a host body into `base` can reorder list options. Step 1 therefore measures each move before the full comparison. It records the drvPaths of all ten NixOS and darwin toplevels and of every home's activation at the parent, after the secrets module joins `nixos.base` and `darwin.base`, and after the bridge moves. If the bridge move changes any of them, the six per-host `hm-sops-bridge` imports stay where they are and only the secrets module joins the base aspects, measured the same way. No host is declared changed to make the move fit, because the design's claim is that no host changes.
  - A standalone home imports `homeManager.secrets` and sees `{ }`, as it sees `osConfig == null` today.
  - The view's first reader is `vcs-signing.nix` (D10 step 10). The omnigent credential adapter `home/ai/omnigent/credentials.nix` lives under `modules/home` but is host-side: its `osConfig` is the host's own configuration (Context). In step 9 it reads `osConfig.vanixiets.secrets` in place of `osConfig.clan.core.vars`, and its assertions keep reading `osConfig.sops.secrets` (`:118,178-179,188`) and `osConfig.sops.templates` (`:130`). The view carries only `path` and `placeholder` and has no sops `owner`, `mode` or `sopsFile`, so it cannot carry what those assertions compare. sops-nix's own options are not clan vars, and the seam leaves them alone. Task 11.4 therefore checks for no `osConfig.clan.core.vars` anywhere in `modules/home`, and for no `osConfig.sops` outside that adapter.
- **Rationale**: homes receive secrets through the bridge, beside the age key it already propagates. The bridge is NixOS-only and per-user today, and stibnite, argentum and rosegold homes read their signing key from the host, so the bridge gains a darwin export carrying only the view, and the view is set for every home user rather than only those in `hm-sops-bridge.users`. Filtering by owner gives a home only what it can open. Boundary: source-versus-delivered; the view carries paths, never contents.
- **Alternatives considered**: (a) homes read `osConfig.vanixiets.secrets`. Smaller, but homes keep reading the host's configuration. (b) the view set by the secrets module, leaving the bridge as it is. Equivalent in effect, but it splits home secret delivery between two modules, the bridge for the age key and the secrets module for paths.

### D6: clan inventory services declare and read through the seam

- **Choice**: the `perInstance` NixOS and darwin modules of `clan/services/{hermes-agent,nix-builders,omnigent,openclaw,tincr}/flake-module.nix` and `clan/services/otel-collector/service.nix` write `vanixiets.secrets` like any feature. The settings `openrouterApiKeyGenerator` and `matrixBotPasswordGenerator` keep their names; their descriptions say they name a secret.
- **Import rule**: `nixos.base` and `darwin.base` import the secrets module, so a module that only ever runs on a fleet host needs no import of its own (`nixos/niks3.nix` has none). A module that writes or reads `vanixiets.secrets` imports `flake.modules.<class>.secrets` itself when some configuration evaluates it without `<class>.base`: every NixOS and darwin module of the six clan services above, which clan instantiates from the inventory and which runtime tests load on nodes that import neither base nor the seam (`vm-tests/tincr-mesh.nix:87-130`), and the feature modules that a runtime test or check fixture imports without base: `nixos/omnigraph-backup.nix` (through `nixos.omnigraph`), `nixos/postgresql-backup.nix`, `nixos/fleet-deployer.nix`, `nixos/omnigent-host.nix` and `darwin/omnigent-host.nix`. The module is keyed `vanixiets/secrets` through `flake.lib.exportAs`, so on a host the second import is the same module and is applied once; the NixOS and darwin exports are one module value with one key. Without clan the module defines nothing outside `vanixiets` (D3), so a clan-free node gains only the option.
- **Rationale**: answers proposal question 2. These modules are first-party code inside clan's inventory framework. Their secrets are fleet secrets and would survive a backend swap; their inventory wiring would not. Renaming the settings would touch the inventory instances under `clan/inventory/` for no gain, since the value is the same string.
- **Alternatives considered**: exempt `modules/clan/**` from the rule. It keeps six files as clan readers and leaves cross-feature reads such as `otel-collector`'s of `greptimedb-users` naming a generator.

### D7: obligations read the option for one name and the seam's backend function for the whole tree

- **Choice**:
  - Per-name readers read `hostConfig.vanixiets.secrets.<name>`, paths through the files' read-only fields and custody through `resolved` (D2): `lib/commit-signing.nix:196`, `lib/host-keys.nix:40`, `lib/omnigent-fleet-obligations.nix:183`, `nixos/r2-usage.nix:237`.
  - Whole-tree readers take clan's full generator tree from `flake.lib.secretsBackend.generatorsOf hostConfig`, defined in `modules/system/secrets.nix`: `lib/shared-vars-recipients.nix:43` (`missing`) and `lib/fleet-deployer.nix:306` (`localSecretsOf`). Their logic stays in their files.
