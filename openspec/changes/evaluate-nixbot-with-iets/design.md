## Context

nixbot on magnetite evaluates every push and pull request of `cameronraysmith/vanixiets` and `sciexp/ironstar` with its own patched `nix-eval-jobs` (2.35.4, linking Nix 2.35.6), run as the bare name from the unit PATH inside a bubblewrap sandbox, behind the host evaluation lock (`modules/nixos/nixbot.nix:259-261`, `modules/lib/nix-eval-lock.nix`, `modules/nixos/nix-eval-lock.nix`).
The evaluator runs at 6 workers × 3072 MiB (`nixbot.nix:139-140`); nixbot gives each evaluation its own cgroup whose `memory.max` is the larger of the worker budget, 3072 × (6+1) = 21504 MiB, and what the host can spare when the evaluation starts, MemAvailable plus three quarters of the ZFS ARC less a 2048 MiB reserve (`nixbot/nixbot/nix_eval.py:107-112,379-386`, `build_run.py:194-214`, `memory.py:119-175`), so the ceiling is at least 21504 MiB and moves with the host's free memory: the first recorded evaluation on magnetite, build 2773 on 2026-11-18, ran under 22323 MiB. The unit carries `MemoryHigh = 20G` (`nixbot.nix:246`), a backstop measured to sit above the 18.7 GB evaluation peak of 2026-09.
IFD is off for nixbot through the unit's `NIX_CONFIG` (`nixbot.nix:250`).
The lock wrapper raises the evaluator to `oom_score_adj 900` because `nix-eval-jobs` ≥ 2.35.3 requeues an OOM-killed worker and retries it alone (`nix-eval-lock.sh`), and magnetite's kill-order assertion reads that script (`modules/machines/nixos/magnetite/default.nix:770-782`).

The shadow benchmark on magnetite (`logs/iets-bench-20261118-175044/summary.md`, brainstorm F12) ran nixbot's exact argv through iets 0.2.0 (`numtide/iets@9157ca1a`) and through the lock-wrapped `nix-eval-jobs`: 295 identical drvPaths, outputs, `cacheStatus`, `extraValue` and `system`; user CPU 135-147 s against 409-435 s; whole-tree cgroup peaks of 16.9-18.6 GiB against 15.2-16.2 GiB.
It ran as user cameron outside bwrap with native `iets eval-jobs`, every result was `local`, and no evaluation failed, so the sandbox, the classic command name, the `cached` and `notBuilt` states and a failing evaluation are uncovered.

What exists for measuring an evaluation today: nixbot's `builds.eval_duration_ms` and per-attribute `eval_wall_ms` and `eval_alloc_bytes`, copied into `devloop.ci_build` and `devloop.ci_attribute` (`modules/clan/services/otel-collector/schema.nix:249-250`).
Nothing records an evaluation's memory peak, its ceiling, kernel kills, the evaluator's own kill messages or which evaluator ran.
Under iets, `allocBytes` counts arena bytes, while `nix-eval-jobs` counts the garbage collector's bytes, so `eval_alloc_bytes` changes meaning at the switch.

Stakeholders: the operator, who maintains magnetite and reads the dev-loop view; contributors whose pull requests nixbot evaluates.

## Goals / Non-Goals

**Goals:**
- One structured record per nixbot evaluation, independent of which evaluator runs, in the dev-loop history, reconciled daily and charted.
- A baseline under `nix-eval-jobs` at 6 × 3072 of at least 48 hours, holding Friday 2026-11-20's 22:00 UTC flake-update evaluation, before any switch (D13).
- A paired replay of about twenty already-evaluated commits under both evaluators inside nixbot's real sandbox under the classic command name, covering `cached` and `notBuilt` outputs and a failing evaluation (D13).
- nixbot evaluating with iets behind the same lock, revertible with one change as a safety valve.
- A measured memory budget for magnetite, so that when an evaluation lacks headroom the fleet decides where its room comes from rather than giving up the faster evaluator.
- Memory settings tuned from recorded peaks after the switch, with the decision recorded.

**Non-Goals:**
- A fleet-wide classic shim, iets on developer machines, in direnv or under buildbot (D1).
- Mic92/nixbot#255, `evalWritablePaths`, or any shared or writable evaluation cache (D2).
- Recording buildbot's or `nix-fast-build --remote`'s evaluations, which also pass through the lock wrapper.
- Changing `--max-memory-size`, `evalWorkerCount` or `MemoryHigh` before the measurements exist (D8).
- Moving services off magnetite or resizing it: those are capacity responses D9 may call for, decided by the operator and carried out elsewhere (the fleet-topology initiative for moves).
- Counting routine worker recycling (open question 1).

## Decisions

### D1: No global classic shim
- **Choice**: iets is not installed as `nix`, `nix-build`, `nix-shell` or `nix-eval-jobs` on any host's PATH or as `nix.package`.
- **Rationale**: Mic92 enabled the classic shim on 2026-10-28 and disabled it four days later because his configuration needs IFD (`9af16bdc`); the fleet has IFD paths of its own (`modules/checks/apps.nix:23`, `packages.nix:16`, `catppuccin.nix:42`); shim users keep hitting gaps (brainstorm F11); and the shim would sit under clan deploys, `nix-fast-build --remote` and the lock wrapper.
- **Alternatives considered**: `nixosModules.default` with `iets.classic.enable` (high blast radius, NixOS-only); iets on PATH as `iets` only (harmless, but out of this change's scope, Q3).

### D2: iets replaces only nixbot's evaluator, behind the lock, with no cache sharing
- **Choice**: set `services.nixbot.packages.nix-eval-jobs` to `config.services.nixEvalLock.wrap` of the D3 package; nixbot's sandbox, argv and settings are unchanged.
- **Rationale**: the benchmark's gain is the evaluator itself: `iets eval-jobs` turns its tracing cache off (`src/cli/jobs.rs:227`) and an emptied cache matched warm runs, so the shared writable cache of #255, and the poisoning risk Mic92 raised about it for a service that evaluates outside contributors' pull requests, buy nothing here.
- **Boundary**: vendored versus first-party. nixbot is vendored; only the first-party override at `nixbot.nix:259-261` changes, through the option nixbot already exposes.
- **Alternatives considered**: #255's `evalCommand` (unmerged, conflicting); ScottyLabs' fork with a shared cache at `/var/lib/nixbot/eval-cache` (brainstorm F8).

### D3: A minimal package exposing iets as `nix-eval-jobs`, with nixbot's Nix grafted on
- **Choice**: a first-party derivation named `nix-eval-jobs-iets-<version>` whose `bin/nix-eval-jobs` is a symlink to `${iets}/bin/iets` (the default package of the `iets` flake input), with `passthru = { pname = "nix-eval-jobs"; evaluator = "iets"; version = iets.version; nix = options.services.nixbot.packages.nix-eval-jobs.default.nix; }`. `pname` stays `nix-eval-jobs` so the lock module's guard against unwrapped evaluators, which selects packages by that name (`modules/nixos/nix-eval-lock.nix:53-55`), still sees this package if it ever reaches a PATH unwrapped.
- **Rationale**: the lock wrapper requires `version` and forwards `nix` only if present (`modules/lib/nix-eval-lock.nix:43-49`); nixbot puts `packages.nix-eval-jobs.nix` on its unit PATH (upstream `nixosModules/nixbot.nix:1155-1158`) and links its own package against it (`packages/nixbot.nix:56`); the grafted `nix` is the same derivation the stock package carries, so the patched nix CLI on the unit PATH, the nixbot package, and the lock module's `isWrapped` drvPath comparison (`modules/nixos/nix-eval-lock.nix:56-57`) are unchanged. iets dispatches on `argv[0]`, so the classic name reaches `cmd_eval_jobs` (`src/cli/classic/mod.rs:45`).
- **Boundary**: source versus delivered. The flake input is upstream source; the derivation and its symlink are first-party and are what lands on the unit PATH. The verification is by `nix eval`/`nix build` of magnetite's configuration and a read of the unit PATH on magnetite, never by reading the source.
- **Alternatives considered**: iets' `classic` package grafted with `.nix` (rejected by the operator: it bundles a second Nix closure and shims four other command names, and it is Linux-only); the plain `iets` package (fails at run time: no `bin/nix-eval-jobs`).

### D4: The `iets` flake input carries no `follows`
- **Choice**: `inputs.iets.url = "github:numtide/iets"`, locked at `9157ca1a` or later, with no `inputs.nixpkgs.follows`. The input tracks upstream and the flake-update effect proposes its updates like any other branch-tracking input, on branch `update-iets`; that pull request is merged only after `just eval-identity` passes at its head, which re-measures A147 for the bump, and its result is named in the pull request.
- **Rationale**: the repository's rule against redirecting an upstream input's nixpkgs; the unredirected build is substituted from cache.numtide.com (the benchmark's `/nix/store/jk7bh7cc…-iets-0.2.0`), which is already a fleet substituter (`lib/caches.nix:8`, key at `:21`).
- **Alternatives considered**: `follows = "nixpkgs"` (a local Rust build and an untested toolchain combination).

### D5: One host-side producer of the evaluation record: a fifth nixbot patch
- **Choice**: a patch beside the four at `nixbot.nix:277-286` makes nixbot's evaluation runner, after the evaluator exits and before it removes the evaluation cgroup, log one JSON line through nixbot's own logger (`log.py:25-43`, which writes JSON to the journal) with message `evaluation finished` and the fields of D6. The lock wrapper is untouched.
- **Rationale**: this supersedes the operator's 2026-11-18 wording that the nixEvalLock wrapper emits the record; read at nixbot 171a8c77 the wrapper cannot:
  - it runs inside bubblewrap built with `--unshare-all` and binds only `SANDBOX_ETC_PATHS`, the store, the store database, the daemon socket, the worktree and the gc-roots directory (`nix_eval.py:221-304`), so neither `/run` (the journald socket) nor `/sys` (`memory.peak`, `memory.events`, `cpu.stat`) is visible, and `extra_ro_paths` is hard-coded to the repository clone (`build_run.py:217`);
  - it `exec`s the evaluator (`nix-eval-lock.sh`, last line), so nothing of it is left to write after the evaluator exits;
  - the evaluation cgroup is nixbot's: it creates it and sets `memory.max` (`nix_eval.py:379-386`), reads `memory.events` (`:535-548`) and deletes it right after the run (`:614-615`).
  The producer sits where the cgroup, the exit status, the evaluator's stderr and the journal are all reachable. Main relayed the operator's choice of this option on 2026-11-18.
- **Boundary**: vendored versus first-party. The patch is first-party code carried against vendored nixbot, pinned like the four existing patches; it is written against upstream's structure and naming so it can be offered to Mic92/nixbot (a follow-up, not a task here).
- **Alternatives considered**: (B) keep the producer in the wrapper by turning `exec` into fork-and-wait and patching nixbot to bind the journald socket and the evaluation cgroup into the sandbox (the cgroup namespace hides the path, so nixbot would have to pass it): still a nixbot patch, and it changes the lock's documented lifetime; (C) the wrapper records what it can see and the patch adds the cgroup fields: two producers per evaluation to join.

### D6: The record's fields come from the evaluation cgroup and nixbot's own state
- **Choice**: the record carries `build_id`, `ts` (the `ts` nixbot's JSON formatter stamps on every line, `log.py:27-28`, written as soon as the evaluator has exited, so the patch passes no `ts` of its own), `evaluator` and `evaluator_version` (from the unit environment value `NIXBOT_EVALUATOR=<evaluator> <version>`, which the module sets from the wrapped package's `unwrapped.evaluator or "nix-eval-jobs"` and `version`), `workers` and `max_memory_mib` (nixbot's settings), `memory_max_bytes`, `memory_peak_bytes`, `oom_kill` (the cgroup's `memory.max`, `memory.peak` and `memory.events` `oom_kill`), `wall_ms` (nixbot's existing monotonic measurement), `user_ms` and `system_ms` (the cgroup's `cpu.stat` `user_usec` and `system_usec`), `budget_kills` and `worker_kills` (counts of the two `nix-eval-jobs` stderr messages `memory budget of … exceeded … killing worker` and `evaluation worker … was killed (system out of memory?)`, `src/nix-eval-jobs.cc:322-327,493-497`, counted as nixbot reads stderr), and `exit_status`. It carries no stderr text. When nixbot ran the evaluation without its own cgroup (the limiter's fallback, `nix_eval.py:582-596`), the cgroup fields are absent rather than zero.
- **Rationale**: every field comes from a source that is the same whichever evaluator runs, so the baseline and the iets weeks are comparable; `cpu.stat`'s core counters exist in every cgroup v2 directory, so CPU time is the evaluation's alone, not nixbot's children in general (magnetite's `nixbot.service` cgroup has `cpu.stat` and `memory.peak`, read 2026-11-18, kernel 6.18.60). Under iets the kill counters stay zero, and a killed worker shows as a failed run with `oom_kill > 0` (A144). Recording no text keeps the `devloop-collection` free-text requirement.
- **Alternatives considered**: probing `nix-eval-jobs --version` at startup for the evaluator identity (iets' classic `--version` output is unverified); `getrusage(RUSAGE_CHILDREN)` deltas (nixbot runs other children concurrently).

### D7: The record enters the dev-loop history as `devloop.eval_run`
- **Choice**: `eval_run` joins `flake.lib.otelCollectorSchema.devloop.tables` with key `build_id` and time index `ts`, gets its pipeline and table statement rendered from that allow-list like the other four, and is fed by a `journald/nixbot-eval` receiver on `nixbot.service` that greps `"msg": "evaluation finished"`, parses `body.MESSAGE` as JSON and retains the allow-listed keys, like `journald/gitea-mq`. `devloop-reconcile` gains a daily comparison of the previous UTC day's `eval_run` rows with nixbot's journal lines. The `devloop` view gains charts of `memory_peak_bytes` against `memory_max_bytes` and of `wall_ms` per evaluation, split by evaluator.
- **Rationale**: reuses the one journald-to-table path, the single allow-list, the reconcile the gap requirement already demands for every kind of dev-loop record, and the committed view.
- **Alternatives considered**: a metrics series through Prometheus scrape (no per-evaluation identity, and nixbot's `/metrics` has no such gauge); a separate database (another TTL and exporter for one table).

### D8: Order of operations, and what each gate needs
- **Choice**: (1) the record under stock `nix-eval-jobs`; (2) the canary, a paired replay of the D3 package against the stock evaluator inside nixbot's real sandbox and argv on magnetite, comparing every attribute's derivation for the same commit (D13); (3) the switch as soon as the replay passes P1–P5, at the settings D9's ladder leaves (5 × 3072 after the replay, D10); (4) a tuning decision from the switched week's records. Each gate is the operator's, recorded with the numbers it rests on. (Steps (1) and (3) as revised by the operator on 2026-11-19, Q69: the 48-hour baseline holding Friday's flake update and the Saturday earliest switch are gone, D13.)
- **Rationale**: the operator's order; the switch must be judged against a baseline measured by the same producer.
- **Alternatives considered**: switching straight after the benchmark (the benchmark skipped the sandbox, the classic name and the uncovered cache states).

### D9: Insufficient headroom triggers a capacity decision; revert is only the last rung
- **Choice**: magnetite's primary job is to be the best nixbot server, so a faster evaluator that needs more room is given room, within what the operator will pay for and maintain. Two separate mechanisms:
  - **Escalation ladder** (operator Q88, 2026-11-21, which replaced the revert at once on any failure). A failing or broken production evaluation under iets is (1) rebuilt; a pass is recorded as transient. (2) If the same commit fails again, it is classified: a kill (`worker_kills`, `oom_kill` or `budget_kills` above 0), an `EvalOOMError` among them, is a capacity problem answered by the capacity trigger below, tuning first, not by a revert; an evaluator failure (a crash exit, a derivation difference, or errors nix-eval-jobs does not produce on that commit) is fixed forward, most cheaply by pinning the iets input (unpinned since #4101) back to its last good revision. (3) The one-line revert to the stock package is taken only when the failure blocks merges and no fix or pin is quick, as a deliberate decision recorded in verify.md; it decides nothing about capacity. The fleet alert `IetsEvaluationUnhealthy` detects the failures (task 6.1).
  - **Capacity trigger.** When, in the canary or any later week, an evaluation's `memory_peak_bytes` exceeds 90 % of its own `memory_max_bytes` (the ceiling that evaluation actually ran under, at least 19353 MiB, the 90 % of the 21504 MiB floor, and higher when the host had more to spare; build 2773's was 20091 MiB of 22323), or reaches the service's 20 GiB `MemoryHigh`, which binds below the ceiling whenever the ceiling is above about 22.2 GiB, or any evaluation records `oom_kill > 0`, the operator makes a resource decision, taking the options in order of cost and effort and recording which one and why, with the evaluation record and the D11 budget it rests on:
    - (a) tune the evaluator: `evalWorkerCount` and `--max-memory-size` (D10);
    - (b) reclaim memory on magnetite: a ZFS ARC cap (`zfs_arc_max` is unset today, so `c_max` is 31.8 GB, the whole of RAM), the zram size, or per-service memory limits on the services the budget shows competing; the first, a soft guard on user sessions, is taken before the switch (D14);
    - (c) move non-CI services off magnetite, the subject of a separate fleet-topology initiative;
    - (d) resize the host.
  (c) and (d) are operator decisions taken outside this change; this change records the trigger and the decision, not their execution. Nothing is asked of iets upstream (D12): the whole-evaluation abort on a killed worker is mitigated only by this trigger, the measured headroom and the canary.
- **Rationale**: the operator's revision of 2026-11-18. The 90 % / 20 GiB figure stays as the point at which headroom is no longer comfortable for an evaluator that fails a whole evaluation on one killed worker (A144), but it now opens a decision instead of delivering a verdict; reverting a 3x faster evaluator for lack of memory that can be found more cheaply would optimise the wrong thing.
- **Alternatives considered**: a keep-or-revert threshold (this design's first version, superseded by the operator); lowering `--max-memory-size` pre-emptively (rejected by Q2); making the switch wait for iets to retry killed workers (no such change is requested, D12).

### D10: Evaluator tuning is the first capacity response and a recorded decision
- **Choice**: after the first switched week, and whenever D9's trigger fires, the operator decides whether to change `evalMaxMemorySize` or `evalWorkerCount`, recording the decision in `modules/nixos/nixbot.nix`'s comment table beside the 2026-09 measurements, citing the week's peaks, wall times and kill counts from `devloop.eval_run` and the D11 budget. If tuning cannot restore headroom without giving back the speed that justified iets, the decision moves to D9's (b)–(d).
- **Rationale**: Q2 as revised; tuning is the cheapest response and touches only nixbot; the existing table at `nixbot.nix:117-138` is where readers look for why the numbers are what they are.
- **Taken, 2026-11-19, before the switch.** The replay's P2 tripped once: e527ef7b's cold first iets run at 6 × 3072 reached nixbot.service's 20 GiB `MemoryHigh` (`memory.events` high 94), 90.2 % of its 22707 MiB ceiling, and ran only 1.53× faster than nix-eval-jobs because it was throttled. D9's first rung was taken, 5 workers × 3072 MiB:
  - Same sandbox, two runs each: B peaked 2.4–2.8 GiB below 6 × 3072 (15584 against 18428 MiB on e527ef7b, 16163 against 18624 MiB on a67385bc), at 67.8–72.0 % of its ceilings, with no measurable loss in wall time.
  - A cold first evaluation under B (395ec68b, 2026-10-07, nixpkgs ac1faec4) peaked at 17081 MiB, 77.6 % of a 22008 MiB ceiling, with no high events; at that peak 16148 MiB was anonymous memory and 74 MiB file pages.
  - 6 × 2560 saved as much but recycled workers more. Raising `MemoryHigh` to 22G lowered no peak.
  - The table in `modules/nixos/nixbot.nix` records the choice and the evidence is in verify.md.

### D11: magnetite's memory budget is measured beside every evaluation
- **Choice**: the record's scope grows from the evaluation to the host. What the fleet already stores is kept as is; a magnetite-only probe adds what is missing, and a budget chart sits beside the evaluation charts in the `devloop` view.
  - **Already stored** (read on magnetite's store on 2026-11-18, `fleet` database): ZFS ARC as `node_zfs_arc_size`, `_c`, `_c_min`, `_c_max`, `_hits`, `_misses` and `_memory_throttle_count` (node_exporter keep-list, `modules/clan/services/otel-collector/schema.nix:61-71`); swap use as `system_paging_usage_bytes` (`host_metrics/memory` paging scraper, `flake-module.nix:343-348`); available memory as `system_linux_memory_available_bytes`; kernel OOM kills as `node_vmstat_oom_kill`; per-process resident memory as `process_memory_usage_bytes` for processes of at least 64 MiB (`schema.nix:144-158`); per-unit restarts and state only (`systemd_service_restarts_total`, `systemd_unit_state`).
  - **Missing:** per-unit memory. The collector's `systemd` receiver is configured for restarts only (`flake-module.nix:395-402`), and at the deployed contrib 0.155.0 it has no memory metric at all (`receiver/systemdreceiver/metadata.yaml` at `v0.155.0` lists only `systemd.service.cpu.time` and `systemd.service.restarts`; `systemd.service.memory.usage` and `.usage.max` appear only in later revisions), so no `systemd_service_memory_*` series exists in the store. Per-process resident memory omits page cache and kernel memory charged to a service, and splits a service across its processes. Also missing: zram's own footprint. `system_paging_usage_bytes` counts swapped-out pages at their uncompressed size, not the RAM zram holds for them (on 2026-11-18 zram0 held 4.98 GB of data in 0.55 GB of RAM, `/sys/block/zram0/mm_stat`).
  - **Added:** `flake.modules.nixos.magnetite-memory-budget`, imported by `flake.modules.nixos.nixbot` so it goes wherever nixbot evaluates (and `modules/machines/nixos/magnetite/default.nix` needs no edit): `magnetite-memory-budget.service`, a oneshot on a 60 s timer run as node_exporter's own user, writes `/run/magnetite-memory-budget/memory-budget.prom` by write-then-rename: `vanixiets_unit_memory_current_bytes{unit}` and `vanixiets_unit_memory_peak_bytes{unit}` from systemd's `MemoryCurrent` and `MemoryPeak` (`systemctl show`, which reads the unit's own cgroup `memory.current` and `memory.peak` wherever it is nested: `matrix-synapse.service` sits under `system.slice/system-synapse.slice/`) for each active unit matching a new `schema.nix` list `memoryBudgetUnits`, the same two for `system.slice` and `user.slice` as totals so that "other" is a subtraction, and `vanixiets_zram_orig_data_bytes`, `vanixiets_zram_compr_data_bytes` and `vanixiets_zram_mem_used_bytes` from `mm_stat`. node_exporter there gains its `textfile` collector on that directory, and the five names join `nodeExporterKeep`; one assertion holds the two together, and another keeps the probe off a DynamicUser, whose RuntimeDirectory sits under the root-only `/run/private` where node_exporter cannot read it (the first deploy, 2026-11-18, logged exactly that).
  - **`memoryBudgetUnits`** (magnetite's running services on 2026-11-18 that hold memory or compete with evaluation): `nixbot.service`, `nix-daemon.service`, `greptimedb.service`, `postgresql.service`, `gitea.service`, `gitea-mq.service`, `gitea-runner-nix0.service`, `gitea-runner-nix1.service`, `niks3.service`, `nginx.service`, `matrix-synapse.service`, `docker.service`, `kanidm.service`, `livekit.service`, `coturn.service`, `perses.service`, `opentelemetry-collector.service`, `omnigent.service`, `omnigent-host-*.service` (stored under the owner aliases), `omnigraph-server.service`, `tor.service`, `tincr-vanixiets.service`, `zerotierone.service`, `systemd-journald.service`. No buildbot unit runs on magnetite today (`systemctl list-units --all '*buildbot*'` is empty), so none is listed. An inactive unit writes no series.
  - **The chart** draws `vanixiets_unit_memory_current_bytes` by unit and slice, `node_zfs_arc_size` with `node_zfs_arc_c_max` as its limit, `vanixiets_zram_mem_used_bytes` and available memory (the store keeps no MemTotal), the host-wide series restricted to hosts that write the budget, beside the evaluation peaks; the weekly baseline (task 2.6) adds each unit's maximum, ARC size and zram use.
- **Rationale**: D9's (b)–(d) need to know what competes with evaluation: on 2026-11-18 `nix-daemon.service`'s cgroup peak was 12.97 GB, `nixbot.service`'s 19.24 GB, `greptimedb.service`'s 1.07 GB and `postgresql.service`'s 0.59 GB, while ARC held 5.4 GB with `c_max` at 31.8 GB. cgroup files are what systemd itself reports as `MemoryCurrent` and `MemoryPeak`, include page cache charged to the service, and need no new collector receiver. The textfile route is the one darwin hosts already use (`fleet-ingress-interface` requirement `The darwin probe reports each allow-listed launchd job and the host's disk health in a textfile`).
- **Boundary**: vendored versus first-party. Enabling `systemd.service.memory.usage` in the vendored receiver would be preferable but is not available at the pinned contrib 0.155.0; when a bump brings it, the probe's unit series become redundant and are removed in favour of the receiver (A153; numbered past A148–A152, which the in-flight `bound-fleet-garbage-collection` change takes).
- **Alternatives considered**: per-process `process_memory_usage_bytes` summed by unit (no unit label, misses page cache and processes under 64 MiB); widening the `systemd` receiver's unit allow-list (it has no memory metric at this version); bumping the collector (a fleet-wide change outside this one).

### D12: Nothing is filed upstream to iets
- **Choice**: no issue, pull request or comment goes to `numtide/iets` from this change; the earlier plan to ask iets to retry a killed worker's attribute alone (Q5 as revised, task 3.3) is withdrawn. (Operator, 2026-11-18.)
- **Consequence**: the whole-evaluation abort on a killed worker (A144, verification blocker B2) stays mitigated only by D9's capacity trigger, the measured headroom of the record and the D11 budget, and the canary; no replacement action is added.

### D13: The switch waits for a paired replay, not a week
- **Choice**: the switch condition is a paired replay against a short baseline, read with judgement rather than applied rigidly. (Operator, Q43, 2026-11-18; it replaces the week of baseline of D8's first version.)
  - **Replay set.** About twenty commits of `cameronraysmith/vanixiets` that nixbot has already evaluated: the five heaviest by stock `memory_peak_bytes`, the five slowest by `wall_ms`, the latest flake-update commit, one each whose outputs were all local, partly cached, partly not built, and whose evaluation failed, and the rest drawn at random from recent days.
  - **Runs.** Each commit under both evaluators back to back, alternating which runs first, inside nixbot's real sandbox and argv (6 workers, `--max-memory-size 3072`, through the evaluation lock, so each run gets its own `memory.max`), in a quiet window with no nixbot evaluation running. Every run is tagged, and its window is excluded from the baseline figures.
  - **Criteria.** P1: the same attribute set and the same `drvPath` per attribute, and for the failing commit the same failing attributes. P2: every iets peak at most 90 % of its own `memory.max` and at most 20 GiB. P3: no OOM kill and no worker kill under iets. P4: `cached` and `notBuilt` states behave the same in the job output. P5: no commit more than 10 % slower under iets; a sanity check only, with the speed-up reported, not gated.
  - **Baseline condition.** Removed by the operator on 2026-11-19 (Q69), both parts: (a) at least 48 hours of stock records and (b) those records holding Friday 2026-11-20's 22:00 UTC flake-update evaluation. The paired replay measures what that unpaired baseline stood for, and better, and its set holds three nixpkgs bumps. ### D14: A soft memory guard on magnetite's user sessions before the switch
- **Choice**: on magnetite only, `user.slice` gets `MemoryHigh = 10G` and no `MemoryMax`: above 10 G user sessions are throttled and their memory reclaimed first, and nothing is killed. `nix-daemon.service`, `nixbot.service` and `system.slice` stay as they are, with no new limit. It lands before the switch (task 5.0), as D9's reclaim rung (b), taken in advance. (Operator, Q47, 2026-11-19.)
  - **Regulator.** `flake.modules.nixos.magnetite-user-slice-guard` sets the slice and asserts it: `user.slice` has a `MemoryHigh` and no `MemoryMax`, so the `nixos-magnetite` check fails on either mutant (MemoryHigh missing, MemoryMax present); `checks.x86_64-linux.user-slice-guard-obligations` runs the same judge over fixtures.
  - **Measure.** The budget probe (D11), which already reports `user.slice`'s current and peak memory, also exports the `high` count of its `memory.events` as `vanixiets_unit_memory_high_events{unit="user.slice"}`, so the baseline shows how often the guard throttles.
- **Rationale**: user sessions' evaluation memory is not what warms nixbot's cache; builds through nix-daemon are, and those stay unlimited, so throttling user evaluation keeps the warming while leaving more room for nixbot's evaluations. A soft limit throttles instead of killing an operator's session.
- **Deferred**: a hard `MemoryMax` on `user.slice`, and moving development evaluation off magnetite, wait for CAM-112's development host.
- **Alternatives considered**: a `MemoryMax` now (kills user processes on a host that still carries development work); limiting `nix-daemon` (would slow the builds that warm the cache).

## Risks / Trade-offs

- [Risk] A worker killed for memory fails the whole iets evaluation, and nixbot reports `EvalOOMError` as permanent (`nix_eval.py:676-689`), while the lock's `oom_score_adj 900` makes the evaluator the kernel's first victim → Mitigation: D9's capacity trigger opens a resource decision before kills become routine, on the headroom the record and the budget measure; the canary shows the headroom before the switch; a kill is a capacity problem on D9's escalation ladder, and the revert is its last rung, taken only when merges are blocked and no quick fix exists (Q88). Nothing is asked of iets upstream (D12). magnetite's kill-order assertion keeps passing under iets because it reads the script; the change states this in the assertion's comment rather than leaving its premise silently false.
- [Risk] iets' peak runs 1-2.5 GiB above `nix-eval-jobs`', near `MemoryHigh = 20G`, where throttling made two-system evaluations crawl in 2026-09 → Mitigation: the record's `memory_peak_bytes` against `memory_max_bytes`, the 20 GiB line in the chart, the D11 budget beside it, and D9's capacity decision.
- [Risk] Reclaiming memory from other services (D9 (b)) can degrade them; an ARC cap lowers ZFS read caching for the store and the databases → Mitigation: each reclaim is a recorded decision citing the budget, taken one at a time and watched in the same chart.
- [Risk] The budget probe adds about 60 series to `fleet` on magnetite → Mitigation: `memoryBudgetUnits` is a fixed list, the probe writes nothing for an absent unit, and the series count is checked against the host's cardinality budget at deploy.
- [Risk] iets diverges from Nix 2.35.6 on some expression the benchmark did not exercise (its parity target is 2.34.8; the README calls it "LLM-ware") → Mitigation: the canary's per-attribute derivation comparison over pinned commits including a failing evaluation; nixbot's own `nixbot/nix-build` would fail on a wrong derivation that does not build, but a different derivation that builds is silent, which the canary is there to catch.
- [Risk] R1: iets never reads the flake's `nixConfig`, so on a host whose daemon lacks the fleet's caches its `cacheStatus` loses them → Mitigation: iets runs only in nixbot on magnetite, whose daemon is configured from `lib/caches.nix` (A143).
- [Risk] The canary's `cached` and `notBuilt` states are the first exercise of iets' cache-status path through the daemon from inside bwrap → Mitigation: the canary covers both explicitly.
- [Risk] `eval_alloc_bytes` and per-attribute `eval_wall_ms` change meaning at the switch → Mitigation: the chart splits by evaluator, and the switch's record names the date; dashboards comparing across the switch are labelled.
- [Risk] iets warns on every run that it ignores `plugin-files` and `accept-flake-config`, which nixbot stores as build warnings (`build_run.py:350-359`) → accepted as noise, recorded at the canary.
- [Risk] The patch adds a fifth carried patch on a fast-moving upstream file → Mitigation: it touches only the runner's tail and the stderr reader; a nixbot input bump that breaks it fails the nixbot package build; it is offered upstream.
- [Trade-off] Routine worker recycling is not counted (open question 1) → accepted; the memory peak and kill counts bound what matters for D9's trigger.
- [Trade-off] buildbot's and `nix-fast-build --remote`'s evaluations go unrecorded → accepted; they are out of scope and keep stock `nix-eval-jobs`.
- [Risk] An iets bump changes a derivation nixbot computes → Mitigation: the bump's pull request is merged only after `just eval-identity` passes at its head (A147 re-measured per bump), its result named in the pull request; `checks.x86_64-linux.nix-eval-jobs-iets` checks the bump's package shape, and 6.1's revert remains for a difference found after merge.
