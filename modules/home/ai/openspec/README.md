# openspec vendored claude assets

This directory holds the vendored OpenSpec (`@fission-ai/openspec`) Claude assets and the home-manager module that installs them.
The schema bundles under `assets/schemas/` are hand-maintained, not generated (see `assets/schemas/README.md`); the refresh generates only the OpenSpec skills, from the package pinned by the `llm-agents` flake input: the `openspec-*` workflow skills and, since OpenSpec 2.2, the `openspec` skill, which routes an OpenSpec request to the workflow skill that handles it and carries its own `references/` files.
Since OpenSpec 2.0 (Fission-AI/OpenSpec#2223) the CLI ships only these skills (the `/opsx:*` commands and the `delivery` setting are retired), and since 2.2 `openspec init` and `openspec update` install every file of each skill from the package's `expectedSkillFiles`.
`generate-skills.mjs` calls that function directly, offline; the refresh script vendors its output into the planning-and-development apm package, and the `openspec-vendored-skills` check compares the vendored copies against it, so the two share one generator and neither needs network access.
The function lives in `dist/core/skill-installer.js`, which is internal rather than public API, so the generator fails naming that file if a release moves it.
Never run `openspec init` or `openspec update` in this repository or in any repository whose `.agents/` is apm-managed: OpenSpec writes its skills into `.agents/skills/`, the tree apm regenerates from its manifest and lock, and links each tool's skills folder (such as `.claude/skills/`) into it.
Under 2.1's default global scope the same commands, run in any repository, would write into `~/.agents/skills/` instead, which home-manager materializes for Codex and Pi; the managed `config.json` therefore sets `skillsScope` to `project`.
The schema bundles and config are installed at the user level by the opt-in `programs.openspec` module in `default.nix`: setting `programs.openspec.enable = true` in a home configuration, as each user home that uses OpenSpec and every Omnigent worker does, delivers the schema bundles user-global and writes the global `config.json` (custom profile, 12 workflows, project skill scope; OpenSpec adds the `openspec` skill to any non-empty profile itself); the OpenSpec skills ship separately through the planning-and-development apm package.
The `openspec` router skill is vendored but withheld from delivery to agent sessions by `excludedUpstreamSkills` in `../skills/default.nix`: its text tells agents to run `openspec init` and `openspec update`, forbidden above, and `openspec config profile`, which rewrites the home-manager-managed global `config.json`, and to send `openspec feedback` to the OpenSpec maintainers.
It stays vendored so the `openspec-vendored-skills` check compares the full generated set, and it still ships in the published planning-and-development plugin.
The generated skills are version-portable and byte-identical to upstream's; they carry no version field, and their `metadata.author: openspec` frontmatter is what marks them as generated, since no hand-authored skill sets it.
Do not hand-edit the generated skills; regenerate them with `nix run .#openspec-refresh-vendored-artifacts` (or `just openspec-regen`) after an `llm-agents` input bump instead.
The `openspec-vendored-skills` flake check fails with the diff when the vendored copies differ from the generator's output, so an `llm-agents` bump that changes OpenSpec's skills fails CI until the refresh is committed.
The regeneration script is the flake app's sidecar at `modules/apps/openspec-refresh-vendored-artifacts.sh`.
