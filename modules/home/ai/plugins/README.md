## First-party agent skill corpus

125 skills across 18 apm packages, published as a marketplace any project can install independently of the Nix configurations.
These counts are computed rather than maintained here: `fd --hidden SKILL.md modules/home/ai/plugins/*/.apm/skills` lists one `SKILL.md` per skill, and the census script that would regenerate them belongs to the parked harborize work on branch `fm/vx-harborize-rung0`.
Each group directory carries an `apm.yml` beside its `.apm/` tree and no other manifest.
The two marketplace files and the skills CLI's discovery file are generated from the root `../../../../apm.yml` `marketplace:` block and the group `apm.yml` files by `pkgs/by-name/skills-marketplace`: `../../../../.github/plugin/marketplace.json` (apm's Copilot profile, all 22 groups, read by apm), `../../../../.claude-plugin/marketplace.json` (the 18 skill groups, read by Claude) and `../../../../skills.sh.json` (the 18 `.apm/skills` directories, read by `npx skills`).
After editing a group's name, description or the published list, or adding or removing a group, run `just agents-marketplace` and commit the three files; the `skills-marketplace-drift` check fails until they match, and the generator fails when a group directory is missing from `marketplace.packages`.
The docs site also publishes the first-party skills, never the remote ones, as an Agent Skills discovery index at `https://infra.cameronraysmith.net/.well-known/agent-skills/index.json`; `pkgs/by-name/vanixiets-docs-payload` generates it from the `.apm/skills/` directories at build time, so it needs no regeneration step and changes with the next docs deploy from `main`.
The routes consumers install by, and what each delivers, are tabulated in the docs guide `packages/docs/src/content/docs/guides/consuming-marketplace-plugins.md`.

apm types a group as an apm package because its `apm.yml` sits beside an `.apm/` directory, and deploys every immediate child of `.apm/skills/`.
Adding a skill still means creating `<group>/.apm/skills/<name>/SKILL.md`; there is no registration step.

## Two things that will silently discard your edits

**Twelve skills are CLI-generated.** Every skill whose frontmatter carries `metadata.author: openspec` is regenerated by `../../../apps/openspec-refresh-vendored-artifacts.sh` from the pinned OpenSpec package, which replaces the directory wholesale; the `openspec-vendored-skills` check fails on any vendored copy that differs from what the pinned package generates. Edits to them survive until the next refresh and then vanish without a diff to explain it. All twelve live in `planning-and-development/`, whose four hand-authored siblings — `agentic-planning-development-workflow`, `linear-project-management`, `openspec-bdd-bridge`, `openspec-linear-sync` — are ours to edit. Check the frontmatter before editing anything in that group.

**A source skill is invisible to the build until git tracks it.** Flake sources are git-tracked files only, so a new skill directory is absent from the composed output rather than an error. The symptom is a successful build that silently lacks the skill.

## Delivery pipeline

Composition and delivery are two stages with a filter between them, which is why the composed count and the delivered count differ:

```mermaid
flowchart LR
  A["18 apm packages<br/>.apm/skills/*"] --> B["apm-skills-compose<br/>+ remote apm deps"]
  B --> C{"delivery<br/>exclusion list"}
  C -->|withheld| D["tdd, writing-for-agents, linear-cli"]
  C -->|delivered| E["~/.claude/skills<br/>~/.factory/skills<br/>codex, opencode"]
```

`pkgs/by-name/apm-skills-compose/` flattens the packages plus remote apm dependencies such as superpowers into one tree and records its skill names, and the `nix hash path` of each remote skill, in the committed `skills.json` index; the build fails when the names drift, when a first-party skill differs from its `.apm/skills/` source, or when a remote skill's hash moves (after a deliberate ref or apm bump, review the named skills, then `just agents-skills-index` regenerates the index). `../skills/default.nix` then enumerates that index, applies an exclusion list, and delivers the result. A skill present in the composed output but absent from `~/.claude/skills/` is withheld deliberately, not broken — the exclusions and their reasons are in that file.

## Remote apm dependencies

Five packages declare remote apm dependencies: `planning-and-development`, `version-control-and-forge`, `preferences-code-and-collaboration-conventions`, `preferences-operations-and-reliability` and `preferences-web-platform-and-deployment`.
Each dependency's commit is written only in the declaring package's `apm.yml`, as a full 40-character SHA; no Nix fetcher repeats it.
Nix downloads all of them with apm itself in one fixed-output derivation, `apm-deps-<digest>` (`pkgs/by-name/apm-skills-compose/deps.nix`), under the single `apmDepsHash` in `pkgs/by-name/apm-skills-compose/package.nix`, and the compose installs offline from that download.
The `<digest>` covers every remote entry and apm's version (`pkgs/by-name/apm-skills-compose/guard.nix`, tested by the `eval-apm-guard` check), so a changed ref or apm version renames the download and its build fails with a hash mismatch that prints the new hash, instead of reusing the previous download.
The guard also fails evaluation on a ref that is not a full SHA, on an entry shape it cannot parse, and on superpowers, agency or icskills entries that are not one skill directory each or do not share one ref.
The download fails when the superpowers or icskills skills declared in the group `apm.yml` files, plus those `deps.nix` withholds by name, differ from upstream `skills/` at the pinned commit, so an upstream skill added or removed by a bump has to be declared or withheld explicitly.

To bump a dependency, edit its `ref:` (for superpowers, agency and icskills, every line of the repository together), build `.#apm-skills-compose`, and copy the hash from the mismatch into `apmDepsHash`.
After the change reaches `main`, `just agents-relock` refreshes the root `apm.lock.yaml`.

Six tools ship their agent skill in the same upstream release as their CLI, and the skill's ref must equal the commit the CLI package records:

| Skill repository | Recorded commit |
|---|---|
| `Mergifyio/mergify-cli` | `mergify-cli-bin.sourceRev` |
| `schpet/linear-cli` | `linear-cli.skillSrc.rev` |
| `microsoft/playwright-cli` | `playwright-cli.src.rev` |
| `max-sixty/worktrunk` | `worktrunk-bin.sourceRev` |
| `github/gh-stack` | `gh-stack.sourceRev` (`modules/nixpkgs/overlays/gh-stack.nix`) |
| `polylint/uncomment` | `uncomment-bin.sourceRev` |

`modules/checks/structure/cli-skill-release-alignment.nix` holds one check per pair, a negative control, a refetch of `github/gh-stack` at the recorded commit with nixpkgs' source hash, and a byte comparison of the delivered `playwright-cli` skill with the CLI's source.
For `mergify-cli-bin`, `worktrunk-bin`, `linear-cli` and `uncomment-bin`, `realize-pin` (`nix run .#realize-pin -- <package> <version>`) rewrites the recorded commit and the `apm.yml` ref together through each pin's `apmRef` companion, and recomputes `apmDepsHash` in `pkgs/by-name/apm-skills-compose/hashes.json` through its `fixedOutputHash` companion.

### For marketplace users

`planning-and-development` depends on 15 superpowers skills from `obra/superpowers` v7.0.2 and on agency's `hickey`, `lowy` and `fact-check`, each declared as its own skill directory (`planning-and-development/apm.yml`).
apm therefore installs only those skill directories: neither repository's hooks, agency's subagents nor its rule are installed, and a plain `apm install` of this package succeeds for the `agent-skills`, `claude`, `codex`, `copilot`, `cursor`, `gemini` and `opencode` targets (`logs/apm-marketplace-20261118-134756.log`).
superpowers' SessionStart hook, which loads `using-superpowers` at the start of each session, is deliberately absent; apm 0.36 refuses superpowers' hook files, and upstream declined apm support (obra/superpowers#2681).
For that hook and the plugin experience, install superpowers natively instead (`/plugin install superpowers@claude-plugins-official`, or its README for other harnesses), and either do not install `planning-and-development` alongside it or remove its superpowers lines, so the same skills are not installed twice.
`preferences-web-platform-and-deployment` depends on 41 of the 43 Internet Computer skills of `dfinity/icskills`, each declared as its own skill directory, so apm deploys them flat and nothing else from that repository.
The two it withholds, `autosync-ic-skills` and `autoupgrade-icp-cli`, are one-time installers of a Claude Code SessionStart hook whose script fetches newer skills from skills.internetcomputer.org or upgrades `icp` and `ic-wasm` on every session; the withheld list and its reason sit in `pkgs/by-name/apm-skills-compose/deps.nix`.
`canhelp` is delivered and carries two scripts, pre-approved in its `allowed-tools`, that run `icp canister metadata` and query ic-api.internetcomputer.org when the skill is invoked.
The marketplace supports the apm version this repository builds with (`modules/nixpkgs/overlays/apm.nix`; 0.38 at the time of writing) and later releases.
Older apm may install a group from it yet deploy none of its skills.
Installers other than apm read the generated marketplace files, whose entries name only each package's source directory, so they do not resolve `apm.yml` dependencies and install none of the remote skills.

The `apm-marketplace-consumer` check (x86_64-linux) registers the marketplace from a bare repository of the committed files and installs the 17 groups that declare no dependencies, comparing every deployed skill and staged instructions fragment with its source.
The groups with remote dependencies need the network: `just agents-marketplace-remote` registers `cameronraysmith/vanixiets` at `main` from GitHub and installs all 22 groups, comparing the groups apm registers with `marketplace.packages`.

## Skills CLI

`npx skills add cameronraysmith/vanixiets` lists and installs the 125 first-party skills one by one (`--list`, `--skill <name>`); it finds them through the root `skills.sh.json`, because its default search stops above `<group>/.apm/skills/<name>`.
A group's tree URL, `npx skills add https://github.com/cameronraysmith/vanixiets/tree/main/modules/home/ai/plugins/<group>`, offers that group's skills.
Neither route installs remote skills or instructions groups.
The `skills-cli-discovery` check (x86_64-linux) runs the skills CLI that `llm-agents` pins against a copy of the repository and fails unless it lists exactly the first-party skill directories and installs one with `--skill` unchanged.

## Claude marketplace

In Claude Code, `/plugin marketplace add cameronraysmith/vanixiets` (or `claude plugin marketplace add cameronraysmith/vanixiets`) adds the marketplace, and `/plugin install <group>@vanixiets` installs a group.
In the Claude desktop app, Customize > Plugins > Add marketplace takes the same `cameronraysmith/vanixiets`.
Each of the 18 skill groups is one plugin whose entry carries `skills: ["./.apm/skills"]`, `strict: false` and no version, so installs follow the repository's commits.

The plugins carry only first-party skills.
The 93 remote skills reach users only through apm or this repository's home-manager configuration, and the four `agent-context-*` groups are not offered to Claude.
On a machine where home-manager already delivers the skills to `~/.claude/skills`, installing a plugin loads its skills a second time, namespaced as `<group>:<skill>`.

Two behaviours the Claude file relies on are observed, not documented: that Claude installs a manifest-free entry whose skills sit in the hidden `./.apm/skills` (world assumptions A217 for Claude Code, A218 for the desktop app), and that a plugin without any version follows the marketplace's commits (A219).
The `claude-marketplace-install` check (x86_64-linux) installs every entry with the pinned Claude Code and compares each plugin's skills with its `.apm/skills`, so a Claude Code update that breaks A217 fails there.
No check reaches the desktop app; the public repository `cameronraysmith/skills-marketplace-test` is its fixture, re-tested after each desktop release the operator installs or when Claude's plugin documentation changes:

1. In the desktop app, Customize > Plugins > Add marketplace, enter `cameronraysmith/skills-marketplace-test` (remove and re-add it if already present).
2. Install each of the three layout plugins and confirm each shows all its skills (five, plus `sync-probe` after its follow-up commit).
3. Push a one-line edit to one skill without any version change, run "Check for updates", and confirm the edit arrives.
4. Record the app version, date and result in the Evidence of A218 and A219 in `openspec/specs/world-assumptions/spec.md` (until the `skills-single-source-marketplaces` change is archived, in its `specs/world-assumptions/spec.md`); a failure voids the assumption and moves the skills to `skills/` (design D11 of that change).

## Authoring

`SKILL.md` frontmatter needs a `name` equal to the skill's directory name and matching `[a-z0-9-]`, and a `description` at most 1024 characters; quote any value that starts with `[` or `{`, or YAML reads it as a list or a map.
The `skills-spec-conformance` check (x86_64-linux) runs `skill-validator validate structure` on every skill and fails on its errors; frontmatter fields beyond the Agent Skills specification and files at a skill's root are allowed, and its warnings are printed only.
The description is the entire trigger surface: a skill fires on what its description says, so content added without extending the description is unreachable in practice.

Skills follow a strict one-owner discipline. Each concept has exactly one owning skill, and siblings point at the owner rather than restating it, so an addition that duplicates an existing skill's material is a routing edit rather than new prose.
Prose conventions are in `preferences-code-and-collaboration-conventions/.apm/skills/preferences-prose-clarity/`.

Within `version-control-and-forge`, `mergify-stack` is an unedited upstream mechanism skill from `Mergifyio/mergify-cli`.
`git-stacked-pr-integration` remains the first-party owner of policy, roles, VCS routing, and evidence.

Groups are named for their subject: `preferences-*` packages hold conceptual foundations loaded on topic, and the remaining groups hold operational workflows.

### Suppression and withholding mechanisms

Three separate, independently-operated mechanisms currently suppress or withhold a skill, and nothing before this section collected them in one place.

1. **`disable-model-invocation: true` frontmatter**, set per skill, prevents that skill from auto-triggering on a description match; the skill is still delivered and still invocable by explicit name or slash command. 20 of the 125 skills in this corpus carry the flag set to `true`, and 2 carry it explicitly set to `false`. Factually, all 20 are operational or command-style skills — meta-tooling commands, event-modeling workflow steps, document-conversion utilities, and git/jj/nix operational commands — and none of them are `preferences-*` conceptual-foundation skills; no `preferences-*` skill in this corpus carries the flag.
2. **The delivery exclusion list** (`excludedUpstreamSkills` in `../skills/default.nix`) removes a skill from every delivered harness target (`~/.claude/skills`, `~/.factory/skills`, codex, opencode) even though the skill still exists in the composed tree. It currently withholds `tdd`, `writing-for-agents` and `linear-cli`, each for a documented reason in that file.
3. **A named reference with an explicit loading condition**, in `../../tools/agents-md.nix` (this file's sibling), states a skill's name in the generated context text alongside a stated condition for when to load it, rather than inlining the skill's full body via a path-based force-load prefix and bypassing both delivery and description-based discovery. Only one skill carries this treatment; see "Archived skill index" below for the one that used to carry the old `@` force-load prefix instead.

The `issues-beads-*` family (`issues-beads`, `issues-beads-audit`, `issues-beads-checkpoint`, `issues-beads-evolve`, `issues-beads-init`, `issues-beads-orient`, `issues-beads-prime`, `issues-beads-seed`) previously sat behind mechanisms 1 and 2 above; both are now moot for that family because the eight directories were deleted outright on 2026-08-26, since beads no longer owns the work — Linear and OpenSpec now do. Recover any of them from history, once this deletion is committed, with `git log --diff-filter=D -- modules/home/ai/plugins/beads-issue-tracking-and-session-workflow/.apm/skills/`, which finds the deleting commit by path prefix rather than by a hash that does not exist yet.
